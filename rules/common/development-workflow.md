# 개발 워크플로

전체 개발 파이프라인: 조사 → 설계 → TDD → 리뷰 → 커밋

## 0. 조사·재사용 (구현 전 필수)

새로운 구현 전에 반드시 기존 자료를 먼저 탐색:

- **시스템 프로그래밍**: man 페이지, POSIX 스펙, kernel.org 문서 확인
- **라이브러리 탐색**: 직접 구현 전에 `apt search`, `pkg-config`, `conan`, `vcpkg` 로 기존 라이브러리 확인
- **코드 탐색**: `sgrep`으로 프로젝트 내 유사 패턴 먼저 파악
- **참조 구현**: GitHub에서 유사 기능 오픈소스 확인 후 포팅 또는 래핑 검토
- **웹 개발**: npm, PyPI 패키지 확인 — 유틸리티 코드 직접 작성 금지

> 80% 이상 해결하는 검증된 구현이 있다면 채택을 우선한다.

## 1. 설계 (planner 에이전트)

아래 조건 중 하나라도 해당하면 **planner 에이전트**로 설계 먼저:

- 파일 3개 이상 동시 수정
- 신규 모듈·서비스·라이브러리 도입
- 시스템 레벨 변경 (IPC, 데몬, 커널 인터페이스, 소켓)
- DB 스키마·메모리 레이아웃 변경
- 대규모 리팩터링

단순 버그 수정·설정값 변경은 설계 생략 가능.

## 2. TDD (tdd 에이전트)

```
RED   → 실패하는 테스트 작성
GREEN → 최소 구현으로 통과
CLEAN → 리팩터링
CHECK → 커버리지 80%+ 확인
```

시스템 프로그래밍에서 테스트 어려운 경우:
- 하드웨어 의존성 → mock/stub 으로 격리
- 커널 인터페이스 → 테스트 더블(shim) 적용
- 메모리 검사 → valgrind / ASan 연동

## 3. 코드 리뷰 (code-reviewer 에이전트)

코드 작성·수정 직후 **즉시** 실행:

```
code-reviewer 에이전트 실행
→ CRITICAL·HIGH 이슈 수정
→ MEDIUM 이슈 가능하면 수정
→ 클린 리뷰도 유효한 결과
```

## 4. 커밋·푸시

- 변경사항 검증 후 커밋 (`/verify` 실행)
- 커밋 메시지 형식: `rules/common/git-workflow.md` 참고
- 수정 완료 시 별도 지시 없이 자동 푸시 — main 직접 push 여부는 저장소 규약을 따른다 (PR 요구 시 기능 브랜치→PR)

## 5. 사전 검토 항목

머지·푸시 전 확인:

- [ ] CI/CD 자동화 검사 통과
- [ ] 메모리 검사 통과 (시스템 코드)
- [ ] 브랜치가 대상 브랜치와 최신 상태
- [ ] 하드코딩된 비밀값 없음
