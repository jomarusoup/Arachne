# 공통 패턴

## 불변성 (매우 중요)
항상 새로운 객체를 생성하고, 기존 객체를 절대 변경하지 마십시오.

// Pseudocode
WRONG:  modify(original, field, value) → changes original in-place
CORRECT: update(original, field, value) → returns new copy with change
근거: 불변 데이터는 숨겨진 부작용을 방지하고, 디버깅을 용이하게 하며, 안전한 동시성을 가능하게 합니다.

## 파일 정리

작은 파일 여러 개 > 큰 파일 몇 개:

- 높은 응집력, 낮은 결합도
- 단일 도메인·단일 책임 기준으로 파일을 구성 — 줄 수는 점검 트리거 (200~400줄 권장, 800줄 초과 시 도메인 분리 여부 점검)
- **줄 수는 한도(limit)가 아니다** — C/C++처럼 언어 특성상 장황해지거나(헤더 주석·에러 경로·
  플랫폼 분기) 응집도 높은 단일 도메인 파일은 800줄을 넘어도 무방하다. 분리 판단 기준은
  "서로 독립적으로 진화하는 역할이 한 파일에 동거하는가"이지 줄 수 자체가 아니다.
- 대형 모듈에서 유틸리티를 추출합니다.
- 유형별이 아닌 기능/도메인별로 정리하세요.

## 점검 트리거 (수치 기준)

일반적인 오류 처리·입력 검증 원칙은 기본 동작이므로 생략한다. 이 프로젝트에서
다른 값을 쓰는 임계치만 남긴다:

- 함수 50줄 초과 → 단일 역할인지 점검
- 파일 800줄 초과 → 도메인 분리 여부 점검 (줄 수는 한도가 아니라 트리거)
- 중첩 4단계 초과 → 구조 점검
- 하드코딩 값 → 상수·설정 파일로
