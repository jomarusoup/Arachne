# GitHub 이슈 처리 워크플로

> 문제와 원인은 issue에 기록하고, 실행이 결정된 후속 작업과 진행 상태는
> `docs/task/README.md` 규약에 따라 `docs/task/`에서 추적한다.

## 이슈 제목 형식

| 타입         | 의미                     |
| ------------ | ------------------------ |
| `[feat]`     | 신규 기능 추가           |
| `[bug]`      | 기존 동작 오작동         |
| `[refactor]` | 동작 변화 없는 코드 정리 |
| `[remove]`   | 기능·필드·파일 제거      |

## 이슈 착수 전 공통 절차

1. **범위 파악** — 이슈 본문의 영향 파일·모듈을 `sgrep`으로 위치 확인
2. **의존성 확인** — 변경 대상이 다른 모듈에서 호출·참조되는지 체크
3. **프로젝트 규칙 확인** — 해당 프로젝트의 `CLAUDE.md`에서 파일 구조·네이밍 규칙 확인

> 프로젝트별 파일 구조·grep 키워드 매핑은 각 프로젝트의 `CLAUDE.md`에서 정의한다.
> 이 파일은 타입별 처리 원칙만 담는다.

---

## [feat] 처리 규칙

1. **planner 에이전트로 설계 먼저** — 파일 3개 이상 수정, 신규 모듈 도입, 시스템 레벨 변경은 반드시 계획 선행
2. **데이터 구조 변경** — 저장소(DB, 파일, 메모리 레이아웃) 변경 시 마이그레이션·하위 호환성 처리 필수
3. **인터페이스 변경** — 공개 API·함수 시그니처 변경 시 모든 호출부 업데이트 확인
4. **단계적 구현** — Phase 1(최소 동작) → Phase 2(핵심 경로) → Phase 3(엣지 케이스) 순서로 진행

## [bug] 처리 규칙

1. **재현 조건 먼저** — 버그가 발생하는 입력·상태·환경을 명확히 정의
2. **근본 원인 파악** — 증상(오동작)과 원인(코드 결함)을 분리해서 분석
3. **최소 수정** — 버그 수정 범위를 최소화, 주변 코드 불필요한 정리 금지
4. **회귀 방지** — 수정 후 동일 버그 재발 방지를 위한 검증 조건 확인

## [refactor] 처리 규칙

1. **동작 보존이 전제** — 외부 동작 변화 없이 내부 구조만 개선
2. **SRP 기준** — 함수·파일이 여러 역할을 담당하면 분리, 줄 수가 아닌 역할로 판단
3. **점진적 변경** — 한 번에 대규모 변경 금지, 검증 가능한 단위로 나눠 진행
4. **테스트 선행** — 리팩터링 전 기존 동작을 검증하는 테스트가 있어야 함

## [remove] 처리 규칙

1. **참조 전수 조사** — 제거 대상을 사용하는 모든 호출부·의존 모듈 확인 (`sgrep`으로 탐색)
2. **저장소 영향 확인** — DB 스키마·파일·메모리 구조 변경 시 기존 데이터 마이그레이션 필요 여부 판단
3. **하위 호환성** — 외부에 노출된 API·인터페이스 제거 시 deprecation 처리 또는 버전 명시

---

## 이슈 처리 순서

```
/issue 커맨드로 최신 목록 확인
→ 낮은 번호(오래된 이슈) 또는 높은 우선순위부터 처리
→ [refactor] · [bug] 먼저, [feat] 나중
→ 처리 완료 시 gh issue close 로 닫기
```

## code-reviewer 연동

모든 이슈 처리 완료 후 `code-reviewer` 에이전트로 변경사항 리뷰:

| 타입         | 확인 포인트                        |
| ------------ | ---------------------------------- |
| `[feat]`     | CRITICAL·HIGH 없으면 머지          |
| `[bug]`      | 수정 범위가 버그 원인에 국한됐는지 |
| `[refactor]` | 동작 변화 없음 확인                |
| `[remove]`   | 참조 누락 없음 확인                |
