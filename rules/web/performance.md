# 웹 성능 예산

> 웹·Electron 렌더러의 사용자 체감 성능 기준이다.
> 최적화 기법(메모이제이션·가상화·코드 분할)은 스킬 `frontend-patterns`에 둔다.

## 원칙

- 성능은 예산으로 관리한다. 예산을 넘는 변경은 측정 근거와 함께 머지한다.
- 실험실 측정(Lighthouse)과 실사용 측정(RUM·`web-vitals`)을 구분한다. 판정은 실사용 p75 기준이다.
- 최적화 전에 측정한다. 프로파일 없이 메모이제이션을 추가하지 않는다.

## Core Web Vitals 목표 (p75)

| 지표 | 의미 | 좋음 | 주요 원인 |
|---|---|---|---|
| **LCP** | 가장 큰 콘텐츠가 그려진 시점 | ≤ 2.5s | 느린 서버 응답, 렌더 차단 리소스, 늦게 발견되는 히어로 이미지 |
| **INP** | 입력 후 다음 화면 갱신까지 지연 | ≤ 200ms | 긴 작업(50ms+), 무거운 이벤트 핸들러, 대규모 리렌더 |
| **CLS** | 예상치 못한 레이아웃 이동 | ≤ 0.1 | 크기 없는 이미지·광고, 늦게 삽입되는 배너, 웹폰트 교체 |

- LCP 이미지는 `fetchpriority="high"`를 주고 지연 로딩하지 않는다.
- 이미지·임베드에는 `width`·`height` 또는 `aspect-ratio`로 자리를 예약한다.
- 50ms를 넘는 작업은 나눈다. 무거운 계산은 Web Worker로 옮긴다.
- 급하지 않은 갱신은 `startTransition`·`useDeferredValue`로 입력 응답 뒤로 미룬다.

## 번들 예산

| 항목 | 기본 예산 (gzip) |
|---|---|
| 초기 진입 JS | ≤ 170KB |
| 경로별 추가 청크 | ≤ 100KB |
| 초기 CSS | ≤ 50KB |
| 웹폰트 | 2종 이하, `font-display: swap` |

- 프로젝트 `CLAUDE.md`에 다른 예산이 있으면 그것을 따른다.
- 새 의존성은 추가 전에 크기를 확인한다. 같은 역할의 가벼운 대안이나 네이티브 API를 먼저 본다.
- 배럴 임포트(`index.ts` 재노출)를 피하고 직접 임포트한다. 트리셰이킹이 깨진다.
- 경로·무거운 위젯(차트·에디터)은 동적 임포트로 분리한다.
- 빌드 산출물 크기는 CI에서 비교한다 (`vite build` 리포트, `size-limit` 등).

## 렌더러 성능 예산 (실시간 데이터 화면)

데스크톱 렌더러(Electron)와 실시간 대시보드에 적용한다.

| 항목 | 예산 |
|---|---|
| 프레임 | 60fps 기준 16.7ms, 그중 스크립트 ≤ 8ms |
| 화면 갱신 빈도 | 수신 빈도와 분리. 스트림은 프레임당 1회로 묶어 반영 |
| 메인 스레드 긴 작업 | 50ms 초과 0건 (정상 부하 기준) |
| 힙 증가 | 1시간 정상 부하 후 안정 구간에서 증가 없음 |
| DOM 노드 | 화면당 1,500개 이하, 긴 목록은 가상화 |

- 수신·디코딩은 Worker에서 하고, 메인 스레드는 그리기만 한다.
- 메시지마다 React state를 갱신하지 않는다. 스토어에 누적하고 `requestAnimationFrame` 주기로 알린다.
- 고빈도 숫자 셀은 컴포넌트 리렌더 대신 캔버스나 직접 DOM 갱신을 검토한다.
- 메모리 누수는 DevTools 힙 스냅샷 3회 비교(기준·부하 후·정리 후)로 확인한다.

## 측정 도구

```bash
npx lighthouse <url> --only-categories=performance   # 실험실 측정
npx vite-bundle-visualizer                           # 번들 구성 확인
```

브라우저 DevTools Performance 패널에서 긴 작업과 레이아웃 이동을 확인한다.
React DevTools Profiler로 불필요한 리렌더를 찾는다.
