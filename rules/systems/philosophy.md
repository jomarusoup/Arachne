# 시스템 프로그래밍 철학 (C · C++ · Rust)

> 골격은 Kernighan & Pike, *The Practice of Programming*(TPOP)이다. 절 번호는 원문
> `programming-philosophy.md`와 같다. 선택된 결정은 [decisions.md](decisions.md)에 있다.
> 포매팅·네이밍·헤더는 `rules/<언어>/coding-style.md`가 정본이다. 이 파일은 다시 적지 않는다.
> 언어별 구현 예시는 `rules/{c,cpp,rust}/patterns.md`에 있다.

**우선순위**: 사용자의 현재 지시 > 저장소의 기존 관례 > [decisions.md](decisions.md) > 이 파일.
기존 관례는 스타일에만 우선한다(D01 혼합). 안전성·에러 처리·동시성은 이 파일이 우선한다.
원칙을 어겨야 하면 어기되, 이유를 코드 주석이나 보고에 한 줄로 남긴다.

## 2. 스타일

영리함보다 명료함이 먼저다. 코드는 새벽 장애 상황에서 읽힌다고 가정한다.

- 매직 넘버는 이름 있는 상수로 만든다.
- 같은 일은 저장소 전체에서 같은 관용구로 한다. 새 관용구를 만들기 전에 기존 것을 찾는다.
- 주석은 "무엇을"과 "왜"를 쓴다. "어떻게"는 코드가 말한다. 주석이 필요해 보이면 먼저 다시 쓸 수 있는지 본다.
- 주석과 코드가 어긋나면 둘 다 틀린 것이다. 코드를 바꾸면 주석도 같은 변경에서 고친다.
- 함수는 짧게, 한 가지 일만 한다. 들여쓰기 3단계나 지역 변수 5~10개를 넘으면 분리를 검토한다.
- C 함수형 매크로는 금지한다(D14). 예외는 둘이다. 호출 위치(`__FILE__`·`__LINE__`)를 담는 로그
  매크로와 필드 정의 X-매크로 테이블이다. 예외 매크로도 `do { } while (0)`로 감싸고 인자를 괄호로 보호한다.
- C++은 C++ Core Guidelines를 의미 규범으로 삼는다. 상수는 `constexpr`, 매크로 대신 `inline`·템플릿을 쓴다.
- Rust는 rustfmt 기본값과 clippy를 따른다. `#[allow]`에는 사유 주석을 단다.

## 3. 알고리즘과 자료구조

소수의 기본 구조로 대부분 해결된다. Big-O는 필요조건이고, 실제 성능은 메모리 접근 패턴이 정한다.

- 직접 만들기 전에 표준 라이브러리와 검증된 라이브러리를 찾는다.
- 기본은 연속 메모리다(`std::vector`·`Vec`·C 배열). 연결 리스트는 측정 근거가 있을 때만 쓴다(D07).
  C의 자료구조 선택(정렬 배열 + `bsearch`, 해시, 링버퍼)은 `c-data-structures` 스킬을 따른다.
- 복잡도와 함께 캐시 지역성과 할당 횟수를 본다.
- 스레드·프로세스 간 통신의 기본 구조는 링버퍼다. 읽기가 압도적인 공유 구조는 RCU 계열을 검토한다.
- 공유메모리에 올리는 레코드는 고정 크기로 만들고 포인터 대신 인덱스·오프셋을 담는다.
- Rust에서 순환·양방향 참조가 필요하면 `Rc<RefCell<>>`보다 인덱스 참조나 아레나를 먼저 검토한다.

## 4. 설계와 구현

자료구조를 정하면 설계가 따라온다.

- 코드보다 핵심 자료구조와 소유 관계를 먼저 정한다. 예외 케이스는 조건문보다 데이터 표현을 바꿔 없앤다.
- 불가능한 상태는 표현할 수 없게 만든다. 플래그 조합보다 상태별 enum·타입을 쓴다.
- 경계에서 한 번 파싱해 타입으로 만들고, 내부에서는 재검증하지 않는다("parse, don't validate").
- 확신이 없으면 단순한 방법으로 먼저 맞게 만든다. 최적화는 그다음이다(D06).
- 이벤트 소스는 파일 디스크립터로 통일한다(`timerfd`·`signalfd`·`eventfd`). 이벤트 루프 하나로 다룬다.
- C++은 값 의미론과 RAII가 중심이다. Rule of Zero가 기본이고, 특수 멤버를 정의하면 Rule of Five를 지킨다.
- Rust는 "누가 무엇을 소유하는가"를 먼저 정한다. borrow checker와 반복해 충돌하면 소유 구조를 재설계한다.

### C 캡슐화·다형성 표준 패턴 — 불투명 핸들 + 함수 포인터 인터페이스

C에서 C++의 캡슐화와 다형성이 필요하면 이 패턴 하나로 통일한다.

- **캡슐화**: 헤더에는 `typedef struct Conn Conn;`만 둔다. 구조체 정의는 `.c`에 숨기고,
  `ConnCreate`·`ConnDestroy`와 동작 함수만 공개한다. 핸들은 생성 함수가 할당하고 파괴 함수가 해제한다.
- **다형성**: 동작 테이블 `XxxOps`(함수 포인터 구조체)를 정의한다. 구현마다 `static const` 테이블
  하나를 두고, 핸들은 `ops` 포인터와 구현 상태 `impl`을 함께 가진다. 호출자는 공개 함수만 부른다.
- 테이블은 불변이고 공유된다. 구현 상태의 소유권은 핸들에 있고, 해제는 `ops->destroy`로 한다.
- 선택 사항인 동작은 NULL을 허용하되, 허용 여부를 헤더 주석에 적고 공개 함수에서 검사한다.
- 구현 예시는 `rules/c/patterns.md`의 "불투명 포인터"·"함수 포인터 인터페이스" 절에 있다.

## 5. 인터페이스와 에러 처리

구현을 숨기고, 작고 직교하는 연산만 노출하고, 사용자 몰래 일하지 않는다.

- 올바르게 쓰기는 쉽고 잘못 쓰기는 어렵게 만든다(Meyers).
- 공개 인터페이스는 최소로 노출한다. 외부 인터페이스(프로토콜·CLI·공개 API)는 호환을 지키고,
  내부 API는 호출자까지 함께 고치는 조건으로 바꾼다(D10). 공개 동작은 합의 없이 바꾸지 않는다.
- 자원을 할당하는 함수는 해제 책임이 누구에게 있는지 시그니처나 문서로 밝힌다.
- 복구 가능한 에러는 반환값으로 전파한다. 불변식 위반은 D05를 따른다. 개발 빌드는 즉시 중단하고,
  운영 빌드는 해당 요청만 실패시키고 로그를 남긴 뒤 프로세스를 유지한다.
- 에러를 삼키지 않는다. 무시해야 하면 이유를 주석으로 남긴다.
- 에러는 감지한 곳에서 맥락(무엇을 하다가, 어떤 입력으로)을 붙여 올리고, 처리하는 곳에서 한 번만
  기록한다. 기록하고 올리고 또 기록하지 않는다.
- 시스템 콜·라이브러리 호출의 반환값은 예외 없이 검사한다. `EINTR`·`EAGAIN`·부분 읽기/쓰기를 처리한다.
- 언어별 에러 모델: C는 음수 errno와 `goto` 단일 정리 경로, C++은 D03 경로 분리(핫패스는 `noexcept`
  + 에러 값), Rust는 D04(`thiserror`/`anyhow`)와 `?` 전파다.

## 6. 디버깅

재현이 먼저이고, 그다음 분할 정복이다. 추측하지 않고 관찰한다.

- 고치기 전에 재현 절차를 확보한다. 재현이 안 되면 재현 조건을 좁히는 것부터 한다.
- 가장 최근의 변경을 먼저 의심한다. 범위를 모르면 `git bisect`로 원인 커밋을 찾는다.
- 익숙한 패턴부터 본다: off-by-one, 초기화 누락, 반환값 미검사, 수명이 끝난 포인터, 경계 조건.
- 고친 버그는 재현 테스트로 남기고, 같은 패턴을 저장소에서 검색한다.
- 보고는 가설 → 관찰 증거 → 결론 순서로 쓴다. 증거 없는 결론은 쓰지 않는다.
- 관찰 도구 순서: 로그 → `strace` → `perf` → `tcpdump` → 코어 덤프 → `gdb`. 자원 점검은 USE Method
  (사용률·포화도·에러)로 빠짐없이 한다.
- 메모리·UB·동시성 의심은 ASan·UBSan·TSan 빌드로 먼저 재현한다. 재현이 어려우면 `rr`을 검토한다.
  Rust `unsafe` 모듈의 이상 동작은 Miri로 먼저 본다.

## 7. 테스트

기능과 테스트는 같은 변경에 넣는다. 버그 수정은 재현 테스트가 먼저다(D15).

- 경계 조건(0, 1, 최대값, 빈 입력, 가득 찬 버퍼)을 먼저 테스트한다.
- 에러 경로가 정상 경로보다 위험하다. 연결 끊김·부분 쓰기·시간 초과·디스크 가득 참을 장애 주입으로 검증한다.
- 단순 참조 구현과 최적화 구현의 결과를 비교하는 차분 테스트를 쓴다.
- 외부 입력을 파싱하는 코드는 퍼징 대상이다(C/C++ libFuzzer, Rust `cargo fuzz`·proptest).
- 테스트 빌드에는 새니타이저를 켠 구성을 포함한다.

## 8. 성능

측정 없이 최적화하지 않는다. 비용 모델의 중심은 연산이 아니라 메모리 접근이다.

- 핫패스는 코드 주석 `/* HOTPATH */`(C)·`// HOTPATH`(C++·Rust)로 표시한다(D06). 핫패스는 설계 단계부터
  할당·분기·캐시를 고려하고, 그 밖의 코드는 측정으로 병목이 확인될 때만 최적화한다.
- 순서: 더 나은 알고리즘·자료구조 → 컴파일러 옵션 → 코드 튜닝(캐싱·전용 할당자·버퍼링·사전 계산).
- 전후를 같은 조건에서 측정하고 수치를 남긴다. 평균이 아니라 꼬리 지연(p99·p99.9)을 본다.
  벤치마크는 운영과 비슷한 캐시 상태·데이터 분포·동시 부하에서 한다.
- 핫패스에서는 동적 할당, 예외, 가상 호출·간접 호출, 숨은 복사, 동기 로그를 피한다.
- 시스템 콜 횟수를 줄인다: 배칭, 제로카피(`sendfile`·`splice`), io_uring.
- 캐시라인 정렬로 거짓 공유를 막고, 스레드별 데이터로 공유 자체를 없앤다.
- 분기 예측 힌트는 측정 근거가 있을 때만 쓴다. 중요한 경로는 생성된 어셈블리를 확인한다.

## 9. 이식성

표준에 기대고, 플랫폼 의존 코드는 격리한다.

- 서버 티어는 리눅스 전용 API(epoll·timerfd·io_uring)를 쓸 수 있다. 단, 한 모듈에 격리하고 사용 지점을
  주석으로 표시한다(D08). 클라이언트는 런타임 이식성에 맡긴다.
- 정수 크기·부호·바이트 순서·정렬·평가 순서에 기대지 않는다. 기대야 하면 명시한다.
- 고정 크기 타입(`<stdint.h>`·`<cstdint>`)을 쓴다. 와이어 프로토콜과 파일 포맷은 바이트 순서와 필드
  크기를 명세에 고정하고(D09), C 구조체 크기는 `_Static_assert`로 고정한다.
- 바이트 순서 변환은 전용 헬퍼(`htobe32` 계열)로 한다.
- 부호 있는 정수 오버플로, 엄격한 별칭 위반, 정렬되지 않은 접근 같은 UB를 피한다. Rust는
  `wrapping_*`·`checked_*`·`saturating_*`로 의도를 밝힌다.

## 10. 표기법

문제에 맞는 표기법(스키마·테이블·코드 생성)을 만들면 문제가 쉬워진다.

- 손으로 반복해 쓰는 코드(메시지 정의·상태 테이블·직렬화)는 스키마와 생성기로 바꿀 수 있는지 본다.
  C에서는 필드 정의 X-매크로 테이블이 그 수단이다(D14 예외).
- 생성 코드는 생성기와 스키마만 커밋하는 것을 권장한다. 생성 명령은 빌드에 넣는다.
- 같은 셸 한 줄을 세 번 쓰면 스크립트로 만든다.
- C++ 컴파일 타임 계산은 `constexpr`·`consteval`로 한다. Rust는 derive와 `macro_rules!`를 쓰고,
  신규 proc macro는 사전 합의한다.

## 11. 동시성

공유 가변 상태가 동시성 버그의 근원이다. 공유를 없애거나, 공유하면 규칙을 문서화하고 도구로 검증한다.

- 기본은 메시지 패싱이다. 데이터를 공유하지 말고 넘긴다(D12).
- 하나의 데이터는 하나의 스레드만 쓴다(단일 작성자). 작성자가 여럿 필요하면 설계부터 의심한다.
- 락을 잡은 채 I/O·사용자 콜백·로그 출력을 하지 않는다. 락 범위는 최소로 한다.
- 원자적 연산은 C11 `<stdatomic.h>`·C++ `std::atomic`·Rust `Atomic*`을 쓴다. 메모리 오더링은 가장
  강한 것(`seq_cst`)에서 시작하고, 약화할 때는 근거를 주석으로 남긴다. `volatile`은 동기화 수단이 아니다.
- 락프리 자료구조의 직접 구현은 최후 수단이다(D12에서 선택하지 않음). 예외는 검증된 단일 생산자-단일
  소비자(SPSC) 링버퍼다. 메시지 패싱 수단으로 쓰고, acquire/release 오더링과 캐시라인 패딩을 갖춘다.
- 동시성 코드는 TSan(Rust는 loom)으로 검증하기 전까지 완료로 보지 않는다.
- 시그널은 `signalfd`나 전용 스레드로 동기 처리한다. 핸들러 안에서는 async-signal-safe 함수만 부른다.
- 핫패스 스레드는 코어 고정과 busy-poll을 검토한다. Rust는 주변부만 Tokio, 핫패스는 전용 스레드다(D13).

### 공유 가변 상태 허용 조건 (D12 — 공유메모리-DB 데이터 계층)

공유메모리처럼 공유 가변 상태가 설계의 전제이면 허용한다. 단, 다음을 모두 지킨다.

1. **락 순서 문서화**: 락 획득 순서를 모듈 헤더 주석이나 설계 문서에 적고 지킨다.
2. **동기화 방식 선택**: 다중 작성자는 robust 프로세스 공유 뮤텍스(`PTHREAD_PROCESS_SHARED` +
   `PTHREAD_MUTEX_ROBUST`)를 쓴다. 읽기가 대부분이면 단일 작성자 + 시퀀스 락을 쓸 수 있다.
3. **robust 복구**: `pthread_mutex_lock`이 `EOWNERDEAD`를 반환하면 보호 대상의 정합성을 검증·복구한
   뒤 `pthread_mutex_consistent`를 호출한다. 복구할 수 없으면 손상 상태로 표시하고 DB에서 다시 적재한다.
4. **attach 시 검증**: 세그먼트 헤더(매직·버전·레코드 크기·상태 플래그)를 검증한 뒤에만 쓴다.
5. **금지**: 공유메모리 안의 포인터, 락 없는 다중 작성, 헤더 검증 없는 attach.

세부 절차는 `shm-db-patterns` 스킬을 따른다. C++의 원시 동기화는 의도가 드러나는 추상화(작업 큐 등)로
감싸고, Rust에서 `Arc<Mutex<T>>`가 퍼지면 소유 구조를 재설계한다.

## 12. 위임용 압축본

C/C++/Rust 작업을 서브에이전트에 위임할 때 아래 블록을 프롬프트에 그대로 붙인다.
paths 규칙은 서브에이전트에 로드되지 않기 때문이다.

```
[시스템 프로그래밍 철학 — 핵심] (정본: rules/systems/philosophy.md)
1. 명료함 > 영리함. 함수는 짧게, 한 가지 일만. 새벽 장애 중에 읽힐 코드로 쓴다.
2. 자료구조와 소유 구조를 먼저 정한다. 예외 케이스는 데이터 표현으로 없앤다. 불가능한 상태는 표현 불가능하게.
3. 인터페이스는 작고 직교하게, 올바르게 쓰기 쉽게. 공개 동작은 합의 없이 바꾸지 않는다.
   C 캡슐화·다형성은 불투명 핸들 + 함수 포인터 인터페이스(ops 테이블)로 한다.
4. 에러는 삼키지 않는다. 복구 가능한 에러는 반환값으로, 불변식 위반은 D05(개발 중단·운영 요청 격리).
   모든 시스템 콜 반환값을 검사하고 EINTR·EAGAIN·부분 I/O를 처리한다.
5. 자원 해제는 구조로 강제한다(RAII, Drop, goto 단일 정리 경로).
6. 추측하지 말고 측정한다. HOTPATH 표시 경로는 할당·예외·가상 호출·숨은 복사·동기 로그를 피하고 꼬리 지연을 본다.
7. 공유 가변 상태를 피한다. 단일 작성자, 메시지 패싱 우선. 공유가 불가피하면 락 순서 문서화와
   robust 뮤텍스 복구(EOWNERDEAD → 검증 → pthread_mutex_consistent). 동시성 코드는 TSan/loom 검증 전까지 미완료.
8. UB와 unsafe는 컴파일러와의 계약이다. unsafe는 최소 범위에 가두고 // SAFETY: 주석을 단다.
9. 버그는 재현 → 분할 정복 → 재현 테스트로 고정한다. 가설과 증거를 분리해 보고한다.
10. 변경은 논리 단위 하나씩. 커밋 메시지는 한국어로 "왜"를 쓴다. 스타일 변경과 로직 변경을 섞지 않는다.
결정: D01 스타일만 기존 관례 · D03 C++ 핫패스 noexcept+에러 값 · D08 리눅스 전용 API는 한 모듈에 격리 ·
D11 unsafe 격리+SAFETY · D12 메시지 패싱+락 기반 공유 허용 · D13 핫패스 전용 스레드 · D14 C 함수형 매크로 금지
(로그·X-매크로 예외) · D16 C11/C++20/Rust 2024 · D17 주석·커밋 한국어. 전체는 rules/systems/decisions.md.
```
