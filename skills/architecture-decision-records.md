# 아키텍처 결정 기록 (ADR)

코딩 세션 중 발생하는 아키텍처 결정을 기록한다. 결정이 Slack 스레드·PR 코멘트·누군가의 기억에만 남지 않고, 코드와 함께 살아있는 구조화된 ADR 문서를 생성한다.

## 언제 활성화하나

- 사용자가 명시적으로 "이 결정 기록하자" 또는 "ADR 작성해줘"라고 할 때
- 중요한 대안 사이에서 선택할 때 (프레임워크, 라이브러리, 패턴, DB, API 설계)
- 사용자가 "...로 결정했다" 또는 "Y 대신 X를 하는 이유는..." 이라고 할 때
- 사용자가 "왜 X를 선택했지?"라고 물을 때 (기존 ADR 읽기)
- 아키텍처 트레이드오프를 논의하는 기획 단계

## ADR 형식

Michael Nygard가 제안한 경량 ADR 형식 (AI 지원 개발에 맞게 조정):

```markdown
# ADR-NNNN: [결정 제목]

**날짜**: YYYY-MM-DD
**상태**: proposed | accepted | deprecated | superseded by ADR-NNNN
**결정자**: [참여자]

## 컨텍스트

이 결정이나 변경을 촉발한 이슈는 무엇인가?

[상황·제약·관련 요소를 설명하는 2~5문장]

## 결정

제안하거나 실행하는 변경은 무엇인가?

[결정을 명확히 서술하는 1~3문장]

## 검토한 대안

### 대안 1: [이름]
- **장점**: [이점]
- **단점**: [단점]
- **선택하지 않은 이유**: [구체적인 이유]

### 대안 2: [이름]
- **장점**: [이점]
- **단점**: [단점]
- **선택하지 않은 이유**: [구체적인 이유]

## 결과

이 변경으로 인해 무엇이 더 쉬워지거나 어려워지는가?

### 긍정적
- [이점 1]
- [이점 2]

### 부정적
- [트레이드오프 1]
- [트레이드오프 2]

### 리스크
- [리스크 및 완화 방안]
```

## 워크플로

### 새 ADR 작성

결정 순간이 감지되면:

1. **초기화 (최초 1회)** — `docs/adr/`가 없으면 사용자 확인 후 디렉토리·README.md·template.md 생성. 명시적 동의 없이 파일 생성 금지.
2. **결정 식별** — 핵심 아키텍처 선택 추출
3. **컨텍스트 수집** — 어떤 문제가 촉발했나? 어떤 제약이 있나?
4. **대안 문서화** — 어떤 다른 옵션을 검토했나? 왜 거부됐나?
5. **결과 서술** — 트레이드오프는 무엇인가? 무엇이 더 쉬워지거나 어려워지나?
6. **번호 부여** — `docs/adr/`의 기존 ADR을 스캔하고 증가
7. **확인 후 작성** — 초안 ADR을 사용자에게 검토 요청. 명시적 승인 후에만 작성. 거부 시 초안 폐기.
8. **인덱스 업데이트** — `docs/adr/README.md`에 추가

### 기존 ADR 읽기

사용자가 "왜 X를 선택했지?"라고 물을 때:

1. `docs/adr/` 존재 확인 — 없으면: "이 프로젝트에 ADR이 없습니다. 지금 기록을 시작할까요?"
2. 있으면 `docs/adr/README.md` 인덱스에서 관련 항목 스캔
3. 일치하는 ADR 파일 읽고 컨텍스트·결정 섹션 제시
4. 일치하는 것이 없으면: "해당 결정에 대한 ADR이 없습니다. 지금 작성할까요?"

### ADR 디렉토리 구조

```
docs/
└── adr/
    ├── README.md              ← 모든 ADR의 인덱스
    ├── 0001-use-nextjs.md
    ├── 0002-postgres-over-mongo.md
    ├── 0003-rest-over-graphql.md
    └── template.md            ← 수동 사용을 위한 빈 템플릿
```

### ADR 인덱스 형식

```markdown
# 아키텍처 결정 기록

| ADR | 제목 | 상태 | 날짜 |
|-----|------|------|------|
| [0001](0001-use-nextjs.md) | Next.js를 프론트엔드 프레임워크로 사용 | accepted | 2026-01-15 |
| [0002](0002-postgres-over-mongo.md) | 기본 데이터스토어로 PostgreSQL 선택 | accepted | 2026-01-20 |
```

## 결정 감지 신호

아키텍처 결정을 나타내는 패턴:

**명시적 신호**
- "X로 가자"
- "Y 대신 X를 써야 해"
- "트레이드오프가 있지만 ... 때문에 가치 있다"
- "ADR로 기록해줘"

**암묵적 신호** (사용자 확인 없이 자동 생성 금지)
- 두 프레임워크·라이브러리 비교 후 결론 도달
- 이유가 있는 DB 스키마 설계 선택
- 아키텍처 패턴 선택 (모놀리스 vs 마이크로서비스)
- 인증·인가 전략 결정
- 대안 평가 후 배포 인프라 선택

## 좋은 ADR의 기준

### 해야 하는 것
- **구체적으로** — "ORM 사용" 아닌 "Prisma ORM 사용"
- **왜를 기록** — 무엇보다 근거가 중요
- **거부된 대안 포함** — 미래 개발자는 무엇이 검토됐는지 알아야 함
- **결과를 솔직하게** — 모든 결정에는 트레이드오프가 있음
- **짧게 유지** — ADR은 2분 안에 읽을 수 있어야 함
- **현재 시제** — "X를 사용한다" (미래형 금지)

### 하지 말아야 하는 것
- 사소한 결정 기록 (변수명·포맷 선택)
- 긴 글 작성 — 컨텍스트 섹션이 10줄 초과면 너무 김
- 대안 생략 — "그냥 골랐다"는 유효한 근거가 아님
- 과거 결정 소급 없이 기록 — 원래 날짜 표시
- ADR 방치 — 대체된 결정은 대체물을 참조해야 함

## ADR 생명주기

```
proposed → accepted → [deprecated | superseded by ADR-NNNN]
```

- **proposed**: 논의 중, 아직 확정 안 됨
- **accepted**: 결정이 효력 있고 따르고 있음
- **deprecated**: 더 이상 관련 없음 (기능 제거 등)
- **superseded**: 새 ADR이 이것을 대체 (항상 대체물 링크)

## 기록할 결정 카테고리

| 카테고리 | 예시 |
|---|---|
| **기술 선택** | 프레임워크, 언어, DB, 클라우드 프로바이더 |
| **아키텍처 패턴** | 모놀리스 vs 마이크로서비스, 이벤트 드리븐, CQRS |
| **API 설계** | REST vs GraphQL, 버전 전략, 인증 메커니즘 |
| **데이터 모델링** | 스키마 설계, 정규화, 캐시 전략 |
| **인프라** | 배포 모델, CI/CD 파이프라인, 모니터링 스택 |
| **보안** | 인증 전략, 암호화, 비밀값 관리 |
| **테스팅** | 테스트 프레임워크, 커버리지 목표, E2E vs 통합 균형 |
| **프로세스** | 브랜치 전략, 리뷰 프로세스, 릴리스 주기 |

## 다른 스킬과의 통합

- **planner 에이전트**: planner가 아키텍처 변경을 제안할 때 ADR 생성 권장
- **code-reviewer 에이전트**: ADR 없이 아키텍처 변경을 도입하는 PR에 플래그
