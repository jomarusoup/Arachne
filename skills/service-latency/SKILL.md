# 서비스 경로 지연

사용자가 보는 상태가 얼마나 빠르고 얼마나 신선한지를 서비스 경로 전체에서 다룬다.
외부 API·큐·캐시·엣지·브라우저처럼 여러 프로세스와 네트워크를 거치는 지연이 대상이다.
HFT 유사 인프라를 포함하지만 엔지니어링 관점에만 집중한다.

## 역할 경계

| 질문 | 스킬 |
|---|---|
| 서비스 구간(API·큐·캐시·엣지·렌더)의 지연을 어떻게 나눠 재고 줄이나 | **이 스킬** |
| 한 프로세스 안 핫패스의 나노초~마이크로초 지연을 어떻게 줄이나 | `latency-critical-systems` |
| 초당 처리량과 흐름 제어(백프레셔·손실 정책) | `data-throughput-accelerator`, `stream-pipeline-patterns` |
| 브라우저 렌더 성능 예산(LCP·INP·CLS) | `rules/web/performance.md`, `frontend-patterns` |
| 병목 구간 내부의 CPU 프로파일링 | `performance-profiling` |

## 언제 사용하나

- 사용자 가시 상태가 늦거나 오래된 데이터를 보여 줄 때
- 외부 API·캐시·엣지·스트리밍 중 어디가 느린지 모를 때
- 캐시나 스트리밍 도입이 실제로 신선도를 개선하는지 판단할 때
- 배포된 서비스의 지연을 라이브로 검증할 때

## 지표 분리

모든 것을 "빠르다"로 뭉치지 않는다. 다음을 따로 추적한다.

- p50, p95, p99 지연
- 처리량(throughput)
- 데이터 신선도(freshness age)
- 큐 깊이(queue depth)
- 캐시 히트율
- 외부 API 응답 시간
- 브라우저 렌더 시간
- 부하 하의 정확성
- 실패·재시도 동작

## 핫 패스 매핑

사용자·이벤트에서 최종 가시 상태까지의 경로를 적는다.

```text
소스 이벤트 → 외부 API → 수집 워커 → 큐 → 캐시 → 엣지 라우트
→ 클라이언트 스트림 → 브라우저 렌더 → 사용자 가시 상태
```

각 구간을 따로 측정한다. 구간마다 시작·끝 타임스탬프를 남기면 어디서 지연이 생기는지 보인다.

## 최적화 순서

1. 불필요한 왕복을 없앤다.
2. 안정적인 읽기는 신선도 메타데이터와 함께 캐시한다.
3. 작은 호출·쓰기는 배치로 묶는다.
4. 연산을 데이터나 사용자에 더 가까운 곳으로 옮긴다.
5. 핫 경로와 콜드 경로를 나눈다.
6. 큐가 무한히 커지기 전에 배압(backpressure)을 건다.
7. 스트리밍은 신선도나 UX 개선이 분명할 때만 쓴다.
8. 오래된 데이터·저하된 프로바이더·잘못된 캐시 상태를 감지하는 카나리를 둔다.

## 검증

배포된 서피스가 있으면 라이브로 읽어 검증한다.

- HTTP 타이밍과 응답 헤더
- 프로바이더 신선도 타임스탬프
- 큐나 작업 상태
- 엣지·캐시 상태
- 실제 UI 신선도를 위한 브라우저 검증
- 재시도·저하 모드 주변 로그

시장 데이터나 주문 실행에 가까운 경로에서는 오더북 나이, VWAP 가정, 프로바이더 상태, 킬 스위치 동작도 확인한다.

## 가드레일

- 필수 검증을 생략해서 지연을 줄이지 않는다.
- 빠른 캐시 히트 뒤에 오래된 데이터를 숨기지 않는다.
- 측정 없이 클라이언트 표기만으로 밀리초 단위 동작을 주장하지 않는다.
- 명시적 승인 게이트 없이 라이브 주문·파괴적 마이그레이션·고객 영향 배포를 실행하지 않는다.
- 로그와 벤치마크 산출물에서 비밀값과 개인 페이로드를 뺀다.
