# 부하 측정

대용량 경로가 목표 레이트를 버티는지 숫자로 답할 때 쓴다.

핵심은 하나다. **부하기는 정해진 일정대로 보내고, 지연은 예정 시각부터 잰다.**
이 원칙을 어기면 느린 시스템이 빠르게 보인다(coordinated omission).

처리량 모델·손실 정책 같은 설계 원칙은 `data-throughput-accelerator`가 정본이다.
송신·수신 파이프라인 구현은 `stream-pipeline-patterns`를 본다.
이 스킬은 "어떻게 재고, 어떻게 기록하나"만 다룬다.

## 1. 부하 유형별 도구

| 유형 | 예 | 도구 | 비고 |
|---|---|---|---|
| 요청형 | REST/JSON API | **k6** (`constant-arrival-rate`) | 개방 모델 실행기를 쓴다 |
| RPC형 | gRPC | ghz | 쓸 때만 도입한다. 여기서는 언급만 한다 |
| 스트림형 | 길이 prefix 바이너리 TCP, 시세·이벤트 푸시 | **전용 송신 시뮬레이터** | 범용 도구로는 와이어 형식·시퀀스를 못 맞춘다 |

스트림형 골격은 `templates/project/throughput-poc/`에 있다.
C 송신기 하나와 C·Node 수신기 두 개, 일괄 실행 스크립트가 들어 있다.

## 2. Coordinated omission

부하기가 응답을 기다린 뒤 다음 요청을 보내면(폐쇄 루프), 시스템이 멈춘 동안 부하기도 멈춘다.
멈춘 구간에 보냈어야 할 요청은 아예 측정되지 않는다.
그래서 p99가 실제보다 수십~수천 배 좋게 나온다.

| 방식 | 송신 시점 | 지연 기준 | 결과 |
|---|---|---|---|
| 폐쇄 루프 (잘못) | 이전 응답 직후 | 실제 송신 시각 | 정지 구간이 지워진다 |
| 개방 루프 (맞음) | `start + n / rate` 고정 일정 | **예정 송신 시각** | 정지 구간이 지연으로 드러난다 |

지켜야 할 것은 세 가지다.

- **개방 루프로 보낸다.** 메시지 n의 예정 시각은 `start + n / rate`로 미리 정해진다.
  수신 측이 느려도 일정은 바뀌지 않는다.
- **뒤처지면 묶어서 따라잡는다.** 밀린 메시지를 한 번의 `write`/`writev`로 보낸다.
  기다렸다가 하나씩 보내면 다시 폐쇄 루프가 된다.
- **지연은 `수신 시각 − 예정 시각`이다.** 송신기의 밀림도 지연에 포함된다.
  송신기 자체의 최대 밀림은 따로 기록해 원인을 가른다.

k6는 `constant-arrival-rate`·`ramping-arrival-rate` 실행기가 개방 모델이다.
`vus`+`duration`만 주는 기본 실행기는 폐쇄 모델이므로 처리량 판정에 쓰지 않는다.

```javascript
// orders.k6.js — 초당 2000 요청을 일정하게 도착시킨다
import http from 'k6/http';
import { check } from 'k6';

export const options = {
    scenarios: {
        steady: {
            executor: 'constant-arrival-rate',
            rate: 2000,
            timeUnit: '1s',
            duration: '2m',
            preAllocatedVUs: 200,   // 부족하면 k6가 dropped_iterations 를 보고한다
            maxVUs: 1000,
        },
    },
    thresholds: {
        http_req_duration: ['p(99)<50', 'p(99.9)<200'],
        dropped_iterations: ['count==0'],   // 부하기가 일정을 못 지키면 측정 무효
    },
};

export default function () {
    const res = http.get(`${__ENV.BASE_URL}/api/orders?limit=20`);
    check(res, { 'status 200': (r) => r.status === 200 });
}
```

`dropped_iterations`가 0이 아니면 부하기가 병목이다.
VU를 늘리거나 부하기를 다른 머신으로 옮긴 뒤 다시 잰다.

## 3. 스트림형 — 전용 송신 시뮬레이터

스트림형은 범용 도구 대신 와이어 형식을 그대로 쓰는 송신기를 만든다.
템플릿 송신기(`throughput-poc/sender/poc_sender.c`)의 규약은 다음과 같다.

| 항목 | 규약 |
|---|---|
| 프레이밍 | `[u32 BE 길이][payload]` — `c-system/src/pipeline/frame_codec`과 같다 |
| payload | `kind`, 시퀀스 번호, 예정 송신 시각(시작 기준 상대 ns), 0 채움 |
| 시작 | HELLO 프레임에 송신 시작 시각(단조 ns)을 담는다 |
| 종료 | END 프레임에 총 송신 건수를 담는다 — 수신 측이 유실을 계산한다 |
| 파라미터 | 목표 레이트, 메시지 크기, 지속 시간 |
| 묶음 | 일정보다 밀리면 최대 1024 프레임을 한 `write`로 보낸다 |
| Nagle | `TCP_NODELAY` — 묶음은 애플리케이션이 만든다 |

수신 계측은 다음을 지킨다.

- **메시지마다 할당하지 않는다.** 재사용 버퍼에 이어 붙이고, 완성된 프레임만 해석한다.
  Node에서 `readBigUInt64LE`는 메시지마다 BigInt를 만든다.
  두 개의 `readUInt32LE`로 읽어 Number로 합친다(2^53 미만 값).
- **시계는 chunk당 한 번 읽는다.** 같은 chunk의 메시지는 같은 수신 시각을 쓴다.
- **분위수는 히스토그램으로 낸다.** 지연을 배열에 모으면 그 자체가 GC 부하가 된다.
  로그-선형 버킷(유효 숫자 약 1.5%)이면 수천 칸으로 충분하다.
- **시퀀스로 갭과 역순을 센다.** TCP에서 갭이 나오면 계측 코드의 버그다.
  UDP·멀티캐스트라면 갭이 곧 유실이다.

### 같은 시계 확인

송신 시각과 수신 시각을 빼려면 두 프로세스가 같은 단조 시계를 써야 한다.
같은 호스트라도 시계 종류가 다르면 값이 크게 어긋난다.

| 플랫폼 | Node `process.hrtime.bigint()`와 같은 C 시계 |
|---|---|
| macOS | `clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)` (잠자기 포함) |
| Linux | `clock_gettime(CLOCK_MONOTONIC)` |

macOS의 `CLOCK_UPTIME_RAW`는 잠자기 시간만큼 어긋난다.
실측에서 차이가 수만 초였다.

그래서 수신 측은 HELLO를 받은 순간 `내 시각 − 송신 시작 시각`을 계산한다.
0 이상 1초 미만이면 같은 시계로 보고 지연을 잰다.
아니면 지연은 "측정 안 함"으로 두고 처리량과 갭만 보고한다.
서로 다른 호스트라면 PTP 수준 동기화 없이는 단방향 지연을 재지 않는다.
대신 왕복 지연을 재거나 처리량·갭만 본다.

## 4. 워밍업

첫 몇 초는 버리고 잰다.
JIT 컴파일, 페이지 폴트, TCP 혼잡 창 확장, 커넥션 풀 채우기가 이 구간에 몰린다.

- 요청형: 낮은 레이트로 30초~1분 돌린 뒤 본 측정 시나리오를 시작한다.
  k6는 시나리오를 둘로 나누고 `startTime`으로 잇는다.
- 스트림형: 짧은 PoC는 전체 구간을 쓰되, 초당 표에서 첫 1초가 튀는지 확인한다.
  튀면 앞 구간을 제외하고 다시 계산한다.
- 장시간 안정성은 별도 측정이다. 1시간 이상 돌려 RSS 추세와 p99.9 추세를 본다.

## 5. 서버·DB·클라이언트를 같이 본다

한쪽만 보면 병목을 잘못 짚는다.
같은 시간축에서 세 쪽을 함께 기록한다.

| 대상 | 볼 것 | 수단 |
|---|---|---|
| 서버 프로세스 | CPU(사용자·커널), RSS, 큐 깊이, 송신 밀림 | `pidstat -urh 1`(Linux), `ps -o rss=,%cpu= -p PID`(macOS), 자체 통계 |
| DB | 커밋 지연, 대기 이벤트, 락, 커넥션 수 | PostgreSQL `pg_stat_statements`·`pg_stat_activity`, Oracle `V$SESSION`·`V$SYSTEM_EVENT` |
| 클라이언트·수신기 | 처리량, 지연 분위수, RSS, GC 정지, 이벤트 루프 지연 | 수신기 자체 계측, Node `PerformanceObserver('gc')`·`monitorEventLoopDelay` |
| 호스트 | 코어별 사용률, 소켓 버퍼, 재전송 | `mpstat -P ALL 1`, `ss -tmi`, `netstat -s` |

macOS에서 프로세스를 1초 간격으로 기록하는 최소 루프는 다음과 같다.

```bash
# PID 의 RSS(KB)와 CPU% 를 1초마다 기록한다
pid="${RECEIVER_PID}"
while kill -0 "${pid}" 2>/dev/null; do
    printf '%s %s\n' "$(date +%s)" "$(ps -o rss=,%cpu= -p "${pid}")"
    sleep 1
done > rss-cpu.log
```

## 6. 기록할 것

| 항목 | 정의 | 왜 |
|---|---|---|
| 목표 레이트 | 송신 일정의 건/초 | 판정 기준 |
| 달성 처리량 | 수신 건수 ÷ 첫 수신~마지막 수신 시간 | 목표보다 오래 걸리면 못 버틴 것이다 |
| 수신 시간 / 예정 시간 | 실제 수신 구간 길이 대비 송신 일정 길이 | 뒤처짐을 한눈에 본다 |
| 유실·갭 | 송신 총 건수 − 수신 건수, 시퀀스 갭 횟수 | 손실 정책 위반 확인 |
| p50 / p99 / p99.9 / 최대 지연 | 수신 시각 − 예정 송신 시각 | 꼬리 지연이 판정의 중심이다 |
| CPU | 수신 프로세스 CPU 시간 ÷ 벽시계 시간 | 여유율 판단 (100%면 포화) |
| RSS 시계열 | 1초 간격 | 누수·버퍼 팽창 확인 |
| GC 정지 | 횟수·합계·최대 | 관리형 런타임의 꼬리 지연 원인 |
| 송신 최대 밀림 | 예정 시각 대비 실제 송신 지연 | 부하기 자체가 병목인지 가른다 |
| 환경 | CPU·코어 수·메모리·OS·런타임 버전·전원 상태·localhost 여부 | 재현 조건 |

평균은 판정에 쓰지 않는다.
평균은 꼬리를 숨긴다.

## 7. 결과 표 양식

결과는 `docs/issue/<날짜>-<주제>-result.md`에 남긴다.
결론을 먼저 쓰고, 표와 한계를 뒤에 둔다.

```markdown
| 수신기 | 목표(건/초) | 달성(건/초) | 달성률 | 수신 시간(초)/예정 | 유실/갭 | p50 | p99 | p99.9 | 최대 | 최대 RSS | 수신 CPU | 송신 최대 밀림 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| node | 100,000 | 100,005 | 100.0% | 10.00 / 10 | 0 / 0 | 20 µs | 76 µs | 200 µs | 1.0 ms | 19.5 MB | 55.5% | 493 µs |
```

읽는 법은 세 줄이다.

- 달성률 100%이고 수신 시간이 예정과 같으면 버틴 것이다.
- 수신 시간이 예정보다 길어지고 p99가 수백 ms~초로 뛰면 포화다. 이때 송신 밀림도 함께 커진다.
- CPU가 100%에 붙으면 단일 스레드 수신기의 한계다. 여유율(목표 대비 몇 배까지 버티나)을 함께 적는다.

포화점은 레이트를 올려 가며 찾는다.
요구 레이트에서 버틴 것만으로는 여유를 알 수 없다.
"요구치의 몇 배에서 무너지는가"를 적는다.

## 8. 함정

| 함정 | 증상 | 대응 |
|---|---|---|
| localhost 측정 | 네트워크 지연·대역폭·재전송이 없다. 송신·수신이 같은 코어를 다툰다 | 결론에 "같은 호스트" 한계를 적는다. 최종 판정은 실제 네트워크 두 호스트로 다시 잰다 |
| 노트북 전원 상태 | 배터리·저전력 모드에서 클럭이 내려가 결과가 흔들린다 | 전원 연결 상태를 기록한다(`pmset -g batt`). 같은 조건에서 반복한다 |
| 열 제한 | 긴 측정 후반에 처리량이 떨어진다 | 초당 표를 보고 추세를 확인한다 |
| GC 정지 | 관리형 런타임에서 p99.9가 GC 주기와 겹쳐 튄다 | GC 횟수·최대 정지를 같이 기록한다. 메시지별 할당을 없앤다 |
| Nagle | 작은 메시지가 최대 수십 ms 묶여 지연이 계단처럼 보인다 | 송신 측 `TCP_NODELAY`. 묶음은 애플리케이션이 만든다 |
| 폐쇄 루프 부하기 | 느려질수록 지연이 좋아 보인다 | 개방 루프 + 예정 시각 기준(2절) |
| 부하기 병목 | 목표 레이트를 송신기가 못 낸다 | 송신 최대 밀림·k6 `dropped_iterations`를 확인한다 |
| 디버그 빌드 | 새니타이저·`-O0` 빌드로 잰다 | 측정은 `-O2` 빌드만. 새니타이저 빌드는 정확성 점검용이다 |
| 출력 비용 | 메시지마다 로그를 찍어 측정 대상이 바뀐다 | 1초 집계만 출력한다 |
| 시계 불일치 | 지연이 음수이거나 수만 초 | HELLO로 같은 시계인지 확인한다(3절) |

## 9. 실행 순서

1. 목표를 적는다. 레이트, 메시지 크기, 허용 p99, 허용 유실(손실 정책).
2. 부하기를 개방 루프로 준비한다. 요청형은 k6, 스트림형은 템플릿 송신기를 복사해 와이어 형식을 맞춘다.
3. 측정용 최적화 빌드를 만든다. 새니타이저 빌드로 먼저 한 번 돌려 정확성을 확인한다.
4. 요구 레이트와 그 위 단계(×2, ×5, ×10)를 잰다. 포화점이 나올 때까지 올린다.
5. 서버·DB·클라이언트 지표를 같은 시간축으로 남긴다.
6. 결과 문서를 쓴다. 결론 → 환경 → 방법 → 표 → 해석 → 한계 → 권고 순서다.

템플릿 사용법은 `templates/project/throughput-poc/README.md`를 본다.
