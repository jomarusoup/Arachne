# 처리량 원칙 허브

대량 데이터 경로의 처리량을 설계하고, 측정하고, 개선할 때 이 스킬부터 본다.
이 스킬은 원칙과 판단 기준을 담는다. 구현 세부는 마지막 절의 트랙 지도가 가리키는 스킬에 있다.

대상 구조는 다음과 같다. 리눅스 C 서버가 메시지를 받아 변환하고, 공유메모리와 DB(Pro*C·ecpg)에
저장하고, 고정 레이아웃 바이너리 프레임으로 TCP 클라이언트에 내보낸다. Rust는 C 모듈의 이식 대상이다.
도메인은 가리지 않는다. 로그·센서·거래·이벤트 데이터 모두 같은 원칙을 따른다.

## 언제 사용하나

- 초당 수만 건 이상을 처리하는 수신·변환·저장·송신 경로를 설계할 때
- 큐가 계속 쌓이거나, 메시지가 사라지거나, 순서가 뒤집힐 때
- DB 쓰기·네트워크 송신·직렬화가 병목으로 의심될 때
- 처리량 개선 PR을 리뷰할 때 (손실·중복·순서 위반을 만들지 않았는지)

### 언제 사용하지 않나

- 요청 하나의 지연을 줄이는 핫패스 기법 → `latency-critical-systems`
- CPU 프로파일링 도구 사용법 → `performance-profiling`
- 큐·I/O·프레이밍 구현 코드 → `stream-pipeline-patterns`

## 1. 처리량 모델

숫자로 먼저 설계한다. 감으로 큐 크기와 스레드 수를 정하지 않는다.

| 기호 | 의미 | 예시 단위 |
|---|---|---|
| λ (도착률) | 단위 시간에 들어오는 메시지 수 | 건/초 |
| μ (서비스율) | 한 단계가 단위 시간에 처리할 수 있는 최대 수 | 건/초 |
| ρ = λ / μ (사용률) | 단계가 바쁜 비율 | 0~1 |
| L | 시스템 안에 머무는 평균 메시지 수 | 건 |
| W | 메시지 하나가 시스템에 머무는 평균 시간 | 초 |

**리틀의 법칙**: `L = λ × W`. 큐 깊이와 체류 시간은 서로를 결정한다.
초당 20만 건이 들어오고 평균 체류가 5ms이면, 안에 머무는 메시지는 평균 1,000건이다.
관측한 큐 깊이가 이 값보다 훨씬 크면 어딘가에서 체류 시간이 늘어난 것이다.

**여유율(headroom)**: 지속 부하에서 사용률을 0.7 이하로 유지한다.
대기 시간은 사용률이 1에 가까워질수록 급격히 커진다(단순 큐 모델에서 `ρ / (1 − ρ)`에 비례).
사용률 0.5에서 대기 계수는 1이고, 0.9에서는 9, 0.99에서는 99다.
따라서 평균 부하가 아니라 **지속 피크 부하**를 기준으로 μ를 확보한다.

**파이프라인 처리량은 가장 느린 단계가 정한다.** 수신 50만·변환 80만·DB 저장 15만 건/초이면
전체 처리량은 15만 건/초다. 다른 단계를 아무리 빠르게 해도 소용없다.

### 버스트 버퍼 산정 (예시)

버퍼는 "버스트 동안 쌓이는 양"으로 산정한다. 평소 부하로 산정하지 않는다.

| 항목 | 값 |
|---|---|
| 평소 도착률 | 20만 건/초 |
| 버스트 도착률 | 60만 건/초, 최대 2초 지속 |
| 단계 서비스율 μ | 40만 건/초 |
| 메시지 크기 | 128바이트 |

1. 버스트 중 순증가율 = 60만 − 40만 = 20만 건/초.
2. 버스트 동안 쌓이는 양 = 20만 × 2초 = **40만 건**.
3. 버스트 후 해소 속도 = 40만 − 20만 = 20만 건/초. 해소 시간 = 40만 ÷ 20만 = **2초**.
4. 안전 계수 1.5를 곱하면 60만 건. 링버퍼는 2의 거듭제곱이므로 **2^20 = 1,048,576 슬롯**.
5. 메모리 = 1,048,576 × 128바이트 = **128MiB**.
6. 최악 체류 시간 = 40만 ÷ 40만 = 약 1초. 이 지연을 클라이언트가 허용하는지 확인한다.

허용하지 않으면 버퍼를 키우지 말고 μ를 늘리거나(파티셔닝·배치), 손실 정책을 바꾼다(4절).
버퍼는 지연을 처리량으로 바꾸는 장치다. 버퍼가 클수록 지연도 커진다.

## 2. 측정이 먼저다

병목 위치를 확인하기 전에는 최적화하지 않는다. 추측으로 고친 곳은 대개 병목이 아니다.

- **단계마다** 처리량(건/초·바이트/초)과 지연(p50·p99·p99.9)을 잰다. 평균은 꼬리를 숨긴다.
- **큐마다** 깊이(현재·최대)와 드롭 수를 잰다. 깊이가 계속 커지는 큐의 다음 단계가 병목이다.
- 지연은 메시지에 찍은 수신 시각부터 측정한다. 송신 측이 늦게 보내서 생긴 지연을 놓치지 않는다
  (coordinated omission). 부하 도구와 측정법은 `load-testing`을 따른다.
- 자원은 USE 방법(사용률·포화도·에러)으로 빠짐없이 본다. CPU·메모리·NIC·디스크·DB 세션 순이다.
- 병목을 찾으면 그 단계를 `performance-profiling`으로 프로파일링한다.

병목 위치를 찾는 순서는 다음과 같다.

1. 단계별 처리량을 나란히 놓고 가장 낮은 단계를 찾는다.
2. 그 단계 앞 큐의 깊이가 증가하는지 확인한다. 증가하면 그 단계가 병목이다.
3. 그 단계가 CPU에 묶였는지, I/O 대기에 묶였는지, 락 경합에 묶였는지 구분한다.
4. 원인 하나만 고치고 같은 조건에서 다시 잰다. 수치는 전후를 함께 남긴다.

## 3. 흐름 제어

모든 큐에는 상한이 있다. 상한 없는 큐는 장애를 메모리 고갈로 미룰 뿐이다.

- 큐 생성 시 용량을 정한다. 용량은 1절의 버스트 산정으로 구한다.
- 큐가 가득 차면 무엇을 할지 큐마다 정한다. 정하지 않은 큐는 리뷰에서 반려한다.
- **백프레셔 전파 경로**를 그린다. 마지막 단계가 느려지면 그 신호가 어디까지 거슬러 올라가는지 적는다.

```text
클라이언트 수신 지연 → 클라이언트별 송신 큐 가득 참 → 팬아웃 단계 처리 정책 적용
DB 커밋 지연 → 저장 큐 가득 참 → 변환 단계 대기 → 수신 큐 가득 참 → 소켓 읽기 중지
→ 커널 수신 버퍼 가득 참 → TCP 윈도 0 → 상류 송신자 감속
```

수신 측 소켓 읽기를 멈추는 것은 정당한 백프레셔다. 상류가 감속할 수 없는 프로토콜(UDP 멀티캐스트
등)이면 백프레셔가 끊긴다. 그 지점에는 반드시 손실 정책(4절)과 드롭 계수를 둔다.

### 느린 소비자 처리 — 셋 중 하나를 고른다

| 선택 | 동작 | 맞는 경우 | 대가 |
|---|---|---|---|
| 대기(block) | 생산자가 공간이 날 때까지 멈춘다 | 내부 단계, 전량 보존 채널 | 느린 소비자 하나가 전체를 늦춘다 |
| 드롭(drop) | 새 메시지나 오래된 메시지를 버리고 센다 | 샘플링 허용 채널 | 데이터 손실, 갭 재요청 필요 |
| 병합(coalesce) | 같은 키의 대기 메시지를 최신값으로 덮어쓴다 | 상태 스냅샷 채널(최신값만 의미) | 중간값 손실, 키별 슬롯 필요 |

팬아웃에서는 느린 클라이언트 하나가 다른 클라이언트를 막으면 안 된다. 따라서 클라이언트별 송신
큐에는 대기를 쓰지 않는다. 병합이나 드롭을 쓰고, 계속 밀리면 강등하거나 연결을 끊는다.
구현은 `stream-pipeline-patterns`의 팬아웃 절을 따른다.

## 4. 데이터 손실 정책 — 채널마다 명시 의무

모든 채널(메시지 종류 × 경로)에 손실 정책을 **문서로 적는다.** 적지 않은 채널은 완료가 아니다.
정책은 채널 계약 문서(`api-contracts`)에 둔다.

| 정책 | 의미 | 예 |
|---|---|---|
| 전량 보존 | 한 건도 버리지 않는다. 가득 차면 대기하고, 유실 시 재요청한다 | 주문·결제·원장·감사 이벤트 |
| 최신값 병합 | 키별 최신 상태만 의미가 있다. 중간값은 덮어쓴다 | 장비 상태·센서 현재값·진행률 |
| 샘플링 | 일정 비율이나 주기로만 보낸다 | 모니터링 지표·미리보기 차트 |

채널마다 다음 다섯 항목을 적는다.

```text
채널        : <메시지 종류와 경로>
손실 정책   : 전량 보존 | 최신값 병합(키: <필드>) | 샘플링(<주기·비율>)
가득 참 동작 : 대기 | 병합 | 드롭(오래된 것/새 것)
갭 처리     : 재요청 | 스냅샷 재동기화 | 무시
관측 지표   : 드롭 수·병합 수·갭 수 카운터 이름
```

정책이 같은 큐 안에 섞이면 큐를 나눈다. 전량 보존 메시지가 병합 큐에 들어가면 조용히 사라진다.

## 5. 순서·중복·유실

네트워크와 재시작은 순서를 섞고, 메시지를 두 번 보내고, 일부를 잃는다. 설계에서 이를 전제한다.

- **시퀀스 번호**: 채널(또는 파티션)마다 단조 증가하는 64비트 시퀀스를 붙인다. 순서 보장 범위는
  시퀀스 범위와 같다. 채널 전체 순서가 필요 없으면 키별 시퀀스로 충분하다.
- **갭 감지**: 수신 측은 기대 시퀀스를 들고 있다. `받은 값 > 기대값`이면 갭이다. 갭 구간을 기록하고
  재요청한다. `받은 값 < 기대값`이면 중복이므로 버린다(멱등 적용이면 다시 적용해도 된다).
- **재요청 한계**: 송신 측은 재전송용 최근 N건(또는 T초)을 보관한다. 범위를 벗어난 재요청은
  스냅샷 재동기화로 바꾼다. 보관량은 1절과 같은 방식으로 산정한다.
- **최소 한 번 전달 + 멱등 적용**: "정확히 한 번"은 전달로 얻지 않는다. 최소 한 번 보내고,
  적용 쪽에서 `(채널, 시퀀스)`나 업무 키로 중복을 걸러 결과를 정확히 한 번으로 만든다.
  DB 적재는 시퀀스를 함께 저장하고 이미 적용한 시퀀스 이하를 무시한다.
- **재시작 재동기화 = 스냅샷 + 증분**: 재접속한 소비자는 먼저 스냅샷(현재 상태와 그 시점 시퀀스 S)을
  받고, 이어서 S 다음부터의 증분을 받는다. 스냅샷을 받는 동안 도착한 증분은 버퍼에 모았다가
  `시퀀스 > S`인 것만 적용한다. 공유메모리가 스냅샷 원천이면 `shm-db-patterns`를 따른다.

## 6. 배치와 파이프라이닝

호출당 고정 비용(시스템 콜·DB 왕복·락·캐시 미스)을 여러 메시지에 나눠 낸다.

- 배치 크기를 키우면 처리량은 늘고, 첫 메시지의 대기 지연도 늘어난다. 두 조건으로 배치를 닫는다.
  **"N건이 모이거나 T 마이크로초가 지나면 보낸다."** 부하가 낮을 때는 T가 지연 상한이 된다.
- 배치 크기는 측정으로 정한다. 크기를 두 배씩 늘리며 처리량이 더 늘지 않는 지점을 찾고,
  그 지점에서 p99 지연이 허용 범위인지 확인한다.
- 단계를 나눈다. 수신·해석·변환·저장·송신을 별도 스레드나 루프로 두고 단계 사이를 bounded 큐로 잇는다.
  단계마다 병렬도를 따로 정한다. CPU 단계는 코어 수만큼, I/O 단계는 대기 시간에 맞춰 정한다.
- 단계 간 전달은 메시지 패싱이다. 단일 생산자-단일 소비자 구간은 SPSC 링버퍼를 쓴다
  (`rules/systems/philosophy.md` 11절, 구현은 `stream-pipeline-patterns`).

## 7. 파티셔닝

한 단계의 μ가 부족하면 키로 나눠 여러 작업자에게 맡긴다.

- **키 기반 분배**: `hash(키) % 파티션 수`로 작업자를 정한다. 같은 키는 항상 같은 작업자로 간다.
  따라서 순서는 키 안에서만 보장된다. 키를 넘나드는 순서가 필요하면 파티셔닝하지 않거나,
  병합 단계에서 전역 시퀀스로 다시 정렬한다.
- 파티션 수는 작업자 수보다 크게 잡고(예: 작업자의 4~8배) 파티션을 작업자에 배정한다.
  작업자 수가 바뀌어도 키 재배치가 작다.
- **핫 파티션**: 특정 키에 부하가 몰리면 그 파티션이 전체 처리량을 정한다. 파티션별 처리량과 큐 깊이를
  계측해 찾는다. 대응은 그 키만 병합 정책으로 바꾸거나, 키를 하위 키로 쪼개거나, 전용 작업자를 둔다.
- 파티션별 상태(캐시·시퀀스)는 그 작업자만 쓴다. 단일 작성자 원칙을 지키면 락이 필요 없다.

## 8. 영속화 경계

수신 경로와 저장 경로를 분리한다. DB가 느려져도 수신과 송신은 계속 돌아야 한다.

- 수신·변환 단계는 메시지를 저장 큐에 넣고 바로 다음 메시지로 간다. DB 커밋을 기다리지 않는다.
- 저장 작업자는 저장 큐에서 배치로 꺼내 **호스트 배열**로 한 번에 적재한다(`embedded-sql`의
  호스트 배열 절: `FOR :n` 배열 INSERT, `sqlca.sqlerrd[2]` 처리 건수 확인).
- **쓰기 배치 크기와 커밋 주기**를 따로 정한다. 예: 배열 1,000행씩 INSERT, 커밋은 5,000행 또는
  200ms마다. 커밋 주기가 길수록 처리량은 늘고, 장애 시 다시 적재할 양도 는다.
- 저장 큐 상한에 닿으면 무엇을 할지 정한다. 전량 보존 채널이면 수신까지 백프레셔를 전파하거나
  로컬 파일 스풀에 적재한다. 어느 쪽이든 손실 정책 문서에 적는다.
- 재적재 안전성은 5절의 멱등 적용으로 확보한다. 커밋 전에 죽으면 마지막 커밋 시퀀스부터 다시 넣는다.
- 공유메모리는 최신 상태의 원천, DB는 이력과 복구의 원천이다. 둘의 동기화 규칙은 `shm-db-patterns`를 따른다.

## 9. 관측성

처리량 문제는 지표가 없으면 재현되지 않는다. 단계와 큐마다 같은 이름 체계로 남긴다.

| 대상 | 지표 |
|---|---|
| 단계 | 처리 건수·바이트(누적 카운터), 처리 지연 p50·p99·p99.9 |
| 큐 | 현재 깊이, 구간 최대 깊이, 가득 참 횟수, 드롭 수, 병합 수 |
| 채널 | 시퀀스 갭 수, 재요청 수, 재동기화 수, 중복 폐기 수 |
| 클라이언트 | 송신 큐 깊이, 강등 수, 강제 종료 수 |
| 저장 | 배치 크기 분포, 커밋 지연, 실패·재시도 수 |

- 포화 신호를 경보로 만든다: 큐 깊이가 용량의 50%를 넘어 지속, 드롭 수 증가, 커밋 지연 증가,
  CPU 사용률 0.7 초과 지속.
- 지표는 핫패스에서 단일 작성자 카운터로 올리고, 별도 스레드가 주기적으로 읽어 기록한다.
  핫패스에서 동기 로그를 쓰지 않는다. 주기 처리량 통계 형식은 `operational-logging`을 따른다.

## 10. 개선 순서와 검증

1. 단계별 지표로 병목을 찾는다(2절).
2. 병목 단계의 배치 크기와 커밋 주기를 조정한다(6·8절).
3. 복사·할당·직렬화를 줄인다(`stream-pipeline-patterns`).
4. 그래도 μ가 부족하면 파티셔닝한다(7절).
5. 버스트가 문제면 버퍼를 다시 산정하고, 지연이 허용 범위를 넘으면 손실 정책을 다시 정한다(1·4절).

검증은 같은 입력량·같은 환경·같은 지표로 전후를 비교한다.
처리량이 늘었더라도 다음 중 하나라도 생겼으면 실패다: 손실 정책 밖의 유실, 중복 적용, 순서 위반,
p99.9 지연의 허용 범위 초과, 장시간 실행 시 메모리 증가.

## 11. 메시지 브로커 도입 판단

기본 구조는 서버 직접 스트리밍 + 공유메모리다. 브로커는 다음 중 둘 이상이 맞을 때만 검토한다.

- 생산자와 소비자의 배포·장애 주기가 달라 수 시간 단위 보관이 필요하다.
- 소비자 그룹이 여럿이고 각자 다른 위치부터 다시 읽어야 한다.
- 처리 서버가 여러 대로 늘어 파티션 재배정이 필요하다.

도입하면 지연이 한 홉 늘고 운영 대상이 하나 늘어난다. 이 비용을 측정값과 함께 ADR로 남긴다.
