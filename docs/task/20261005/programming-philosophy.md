## 0. 이 문서의 사용법

### 0.1 구성

이 문서는 세 부분으로 되어 있다.

1. **결정 레지스터(§1)** — 대가들 사이에서 입장이 갈리는 지점. 사용자가 프로젝트별로 하나를 고른다.
2. **원칙 본문(§2~§11)** — 합의된 원칙. 에이전트가 항상 따른다. 결정 사항이 개입하는 곳은 `→ D##`로 표시한다.
3. **위임용 압축본(§12)** — 서브에이전트 위임 시 프롬프트에 그대로 재기술할 핵심 요약.

### 0.2 에이전트 해석 규칙

- `[x]`로 표시된 선택지를 따른다.
- 아무것도 선택되지 않은 결정은 `(기본)` 표시 선택지를 따르고, 작업 보고 끝에 "D## 기본값 적용"이라고 밝힌다.
- 우선순위: **사용자의 현재 지시 > 저장소의 기존 관례(D01 선택에 따름) > 이 문서의 결정 레지스터 > 이 문서의 원칙 본문**.
- 원칙 본문과 결정 레지스터가 충돌하면 결정 레지스터가 이긴다.
- 원칙을 어겨야 하는 상황이면 어기되, 이유를 코드 주석이나 보고에 한 줄로 남긴다. 원칙은 판단의 기본값이지 판단의 대체물이 아니다.

### 0.3 결정 정리 프롬프트 (부트스트랩)

사용자가 "철학 결정 정리", "decision register 정리" 등을 요청하면 에이전트는 다음을 수행한다.

1. §1에서 `[x]`가 없는 결정 항목을 모두 찾는다.
2. 한 번에 최대 4개씩, 선택형 질문(AskUserQuestion 등)으로 사용자에게 묻는다. 각 질문에는 선택지와 각 선택지의 트레이드오프 한 줄, 그리고 `(기본)` 선택지를 첫 번째에 "(권장)"으로 제시한다.
3. 답을 받으면 해당 선택지를 `[x]`로 바꾸고, 결정 항목 아래 `- 결정일: YYYY-MM-DD / 사유: ...` 한 줄을 추가한다.
4. 모든 항목이 정리되면 §0.4의 분할 배치를 제안한다(실행은 사용자 승인 후).

## 1. 결정 레지스터 (Decision Register)

형식: 각 결정은 선택지 중 하나를 `[x]`로 바꾼다. 여러 개를 고를 수 있는 항목은 `(복수 선택)`으로 표시했다.

### D01. 기존 코드 관례 vs 이 문서
대가들 공통: 일관성이 개별 스타일보다 중요하다. 문제는 기존 코드가 이 문서와 다를 때다.
- [ ] (기본) **기존 관례 우선** — 수정하는 파일/모듈의 기존 스타일을 따른다. 이 문서는 신규 모듈에만 적용한다.
- [ ] **이 문서 우선** — 수정하는 부분부터 이 문서에 맞추되, 한 커밋에 스타일 변경과 로직 변경을 섞지 않는다.
- [x] **혼합** — 스타일은 기존 관례, 안전성·에러 처리·동시성 규칙은 이 문서 우선.
- 결정일: 2026-10-05 / 사유: 철학 계획 §3.2 권장(혼합). 기존 Pro*C·C 자산이 있어 스타일은 기존 관례, 안전성 규칙은 이 문서 우선

### D03. C++ 에러 처리 모델
Stroustrup·Sutter는 예외를 기본으로 보고, 저지연·임베디드 진영과 Google 스타일은 예외를 배제한다.
- [x] (기본) **경로 분리** — 초기화·설정·관리 경로는 예외 허용, 핫패스는 `noexcept` + `std::expected`/에러 코드.
- [ ] **예외 기본** — 표준 C++ 관례. 에러는 예외로 전파한다.
- [ ] **예외 금지** — `-fno-exceptions` 전제. 모든 에러는 `std::expected` 또는 에러 코드로.
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D04. Rust 에러 타입 전략
- [x] (기본) **라이브러리는 `thiserror`, 애플리케이션 최상위는 `anyhow`**
- [ ] **수동 enum** — 외부 크레이트 없이 `enum Error` + `impl std::error::Error`.
- [ ] **`snafu`** — 컨텍스트 선택자 기반.
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D05. 불변식 위반 시 동작 (fail-fast vs fail-safe)
TPOP·Rust는 버그를 즉시 드러내라고 하고, 리눅스 커널은 시스템 전체를 멈추는 `BUG_ON`을 경계하고 `WARN_ON`을 권한다. 운영 시스템에서 가장 중요한 결정이다.
- [x] (기본) **계층 분리** — 개발/테스트 빌드는 즉시 중단(assert, panic). 운영 빌드는 해당 요청/세션만 격리 실패시키고 로그·알람 후 프로세스는 유지.
- [ ] **항상 fail-fast** — 불변식 위반은 운영에서도 즉시 프로세스 종료. 재기동·페일오버 체계가 있을 때 적합.
- [ ] **항상 fail-safe** — 로그 후 안전한 기본값으로 계속. 중단 비용이 매우 클 때만.
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D06. 최적화 착수 시점
Knuth·Pike는 측정 전 최적화를 경계하고, Martin Thompson·Carl Cook은 핫패스는 설계 단계부터 성능을 전제해야 한다고 본다.
- [x] (기본) **경로 기반** — 핫패스로 지정된 코드는 설계 단계부터 할당·분기·캐시를 고려한다. 그 외는 측정으로 병목이 확인될 때만 최적화한다.
- [ ] **측정 우선** — 모든 코드에서 명료성 우선, 프로파일링 근거가 있을 때만 최적화.
- [ ] **성능 우선** — 전체 코드베이스를 저지연 기준으로 작성.
- 핫패스 정의 위치: 코드의 `/* HOTPATH */`·`// HOTPATH` 주석
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택. 핫패스 표시는 코드 주석 `/* HOTPATH */`(C) · `// HOTPATH`(C++·Rust)

### D07. 기본 자료구조 선택
- [x] (기본) **표준 컨테이너 우선** — `std::vector`/`Vec` 기본, 필요가 측정으로 증명될 때만 커스텀.
- [ ] **도메인 특화 허용** — 핫패스에서는 침습형 리스트, 고정 크기 링 버퍼, 아레나를 처음부터 허용.
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택. C는 표준 컨테이너가 없으므로 자료구조 선택은 `c-data-structures` 스킬(로드맵 I-1) 기준

### D08. 이식성 범위
- [x] (기본) **리눅스 전용 허용** — epoll, timerfd, io_uring 등 사용 가능. 단, 리눅스 전용 API는 한 모듈에 격리.
- [ ] **POSIX 한정** — 이식 가능한 API만 사용.
- [ ] **커널 바이패스 허용** — DPDK, ef_vi, Onload 등 벤더 API 사용 가능(격리 필수).
- 결정일: 2026-10-05 / 사유: 권장안 채택 + 로드맵 R1 — 서버 티어에 한함. 클라이언트는 런타임(Node·브라우저) 이식성에 위임

### D09. 데이터 교환 형식
TPOP는 텍스트를 권하지만, 저지연 시스템은 바이너리를 쓴다.
- [x] (기본) **경계별 선택** — 설정·로그·관리 인터페이스는 텍스트(TOML/JSON 등), 핫패스 프로토콜은 바이너리.
- [ ] **텍스트 우선** — 디버깅 용이성을 우선한다.
- [ ] **바이너리 우선**
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D10. 내부 API 안정성
리눅스 커널은 외부 ABI는 절대 지키고 내부 API는 자유롭게 바꾼다.
- [x] (기본) **커널 방식** — 외부 공개 인터페이스(프로토콜, CLI, 공개 크레이트 API)는 호환 유지. 내부 API는 호출자까지 함께 수정하는 조건으로 자유롭게 변경.
- [ ] **내부도 안정 유지** — 내부 API 변경 시 폐기 예고(deprecation) 단계를 거친다.
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D11. Rust `unsafe` 정책
- [x] (기본) **격리 허용** — 허용하되 최소 범위의 모듈에 가두고, 모든 `unsafe` 블록에 `// SAFETY:` 주석 필수, Miri 테스트 권장.
- [ ] **금지** — 크레이트 루트에 `#![forbid(unsafe_code)]`. FFI가 필요하면 별도 크레이트로 분리.
- [ ] **성능 목적 허용** — 측정 근거가 있으면 핫패스에서 허용(SAFETY 주석은 동일하게 필수).
- 결정일: 2026-10-05 / 사유: 권장안 일괄 채택

### D12. 동시성 기본 모델 (복수 선택)
- [x] (기본) **메시지 패싱 우선** — 채널/큐로 소유권을 넘긴다. 공유 가변 상태는 예외.

## 2. 스타일 (TPOP 1장)

**핵심:** 영리함보다 명료함. 코드는 새벽 장애 상황에서 읽힌다고 가정하고 쓴다.

[공통]
- 이름의 길이는 스코프에 비례한다. 지역 루프 변수는 `i`로 충분하고, 전역·공개 심볼은 설명적이어야 한다.
- 매직 넘버는 이름 있는 상수로 만든다.
- 같은 일은 저장소 전체에서 같은 관용구로 한다. 새 관용구를 도입하기 전에 기존 관용구를 찾는다.
- 주석은 "무엇을"과 "왜"를 쓴다. "어떻게"는 코드가 말해야 한다. 설명이 필요한 코드는 주석을 달기 전에 다시 쓸 수 있는지 먼저 검토한다.
- 주석과 코드가 어긋나면 둘 다 틀린 것으로 간주한다. 코드를 바꾸면 주석도 같은 변경에서 고친다.
- 포매팅은 도구에 맡긴다(→ D02). 스타일 논쟁으로 리뷰 시간을 쓰지 않는다.

[Linux/C]
- 함수는 짧게, 한 가지 일만. 들여쓰기 3단계를 넘으면 함수 분리를 검토한다. 지역 변수가 5~10개를 넘으면 분리한다.
- 구조체에 불필요한 `typedef`를 쓰지 않는다(불투명 타입 등 명확한 이유가 있을 때만).
- 매크로가 불가피하면 `do { } while (0)`로 감싸고 인자를 괄호로 보호한다(→ D14).

[C/C++]
- C++ Core Guidelines를 의미 규범으로 참조한다.
- 상수는 `constexpr`, 함수형 매크로는 `inline` 함수나 템플릿으로 대체한다.

[Rust]
- rustfmt 기본 설정과 clippy 경고를 준수한다. clippy 경고를 억제할 때는 `#[allow]`에 사유 주석을 단다.
- 네이밍은 Rust API Guidelines를 따른다.

## 3. 알고리즘과 자료구조 (TPOP 2장)

**핵심:** 소수의 기본 구조로 대부분 해결된다. Big-O는 필요조건이고, 실제 성능은 메모리 접근 패턴이 결정한다.

[공통]
- 직접 만들기 전에 표준 라이브러리와 검증된 라이브러리를 찾는다.
- 기본 컨테이너는 연속 메모리(`std::vector`, `Vec`)다. 연결 리스트는 측정 근거가 있을 때만 쓴다(→ D07).
- 자료구조를 고를 때 연산 복잡도와 함께 캐시 지역성, 할당 횟수를 같이 고려한다.

[Linux/시스템]
- 스레드·프로세스 간 통신의 기본 구조는 링 버퍼다.
- 읽기가 압도적인 공유 구조는 RCU 계열 기법을 검토한다.
- 침습형 자료구조(`list_head` + `container_of` 패턴)는 할당 없이 여러 컬렉션에 동시 소속이 필요할 때 쓴다(→ D07).

[Rust]
- 순환 참조나 양방향 링크가 필요하면 `Rc<RefCell<>>`부터 쓰지 말고, 인덱스 기반 참조나 아레나를 먼저 검토한다.

---

## 4. 설계와 구현 (TPOP 3장)

**핵심:** 자료구조를 정하면 설계가 따라온다. 좋은 설계는 언어가 바뀌어도 본질이 같다.

[공통]
- 코드를 쓰기 전에 핵심 자료구조와 그 관계를 먼저 정한다. 예외 케이스를 조건문으로 처리하기 전에, 데이터 표현을 바꿔 예외 자체를 없앨 수 있는지 검토한다(Torvalds의 "good taste").
- 불가능한 상태는 표현 불가능하게 만든다. 플래그 조합보다 상태별 타입이나 enum을 쓴다.
- 경계에서 한 번 파싱해 타입으로 만들고, 내부 코드는 재검증하지 않는다("parse, don't validate").
- 확신이 없으면 단순한 방법(brute force)으로 먼저 맞게 만든다. 최적화는 그다음이다(→ D06).

[Linux/시스템]
- 다형성은 함수 포인터 테이블(ops 구조체)로 구현할 수 있다. 언어 기능이 아니라 자료구조로 해결하는 방법을 먼저 검토한다.
- 이벤트 소스는 파일 디스크립터로 통일한다(timerfd, signalfd, eventfd). 이벤트 루프 하나로 모두 다룰 수 있게 한다.

[C/C++]
- 설계의 중심축은 값 의미론과 RAII다. 객체 생명주기가 곧 자원 생명주기가 되도록 설계한다.
- Rule of Zero를 기본으로 한다. 특수 멤버 함수를 직접 정의해야 하면 Rule of Five를 지킨다.

[Rust]
- "누가 무엇을 소유하는가"를 먼저 정한다. borrow checker와 반복해서 충돌하면 문법으로 우회하지 말고 소유 구조를 재설계한다.
- `clone()`으로 컴파일 에러를 피하는 것은 설계 신호로 취급한다. 핫패스에서는 불필요한 복제를 사유 없이 두지 않는다.

---

## 5. 인터페이스 (TPOP 4장)

**핵심:** 구현을 숨기고, 작고 직교하는 연산만 노출하고, 사용자 몰래 일하지 않는다. 소유권을 명확히 하고, 에러는 낮은 곳에서 감지해 높은 곳에서 처리한다.

[공통]
- 올바르게 쓰기는 쉽고 잘못 쓰기는 어렵게 만든다(Meyers).
- 공개 인터페이스는 최소로 노출한다. 한 번 공개한 것은 약속이다(→ D10).
- 외부 사용자에게 노출된 동작은 버그처럼 보여도 사전 합의 없이 바꾸지 않는다("don't break userspace").
- 함수가 자원을 할당하면, 해제 책임이 누구에게 있는지 시그니처나 문서에서 분명히 한다.

[에러 처리 — 공통]
- 복구 가능한 에러와 버그(불변식 위반)를 구분한다. 전자는 반환값으로 전파하고, 후자는 → D05에 따라 처리한다.
- 에러를 삼키지 않는다. 무시해야 한다면 무시하는 이유를 주석으로 남긴다.
- 에러는 감지한 곳에서 맥락(무엇을 하다가, 어떤 입력으로)을 붙여 올리고, 처리할 수 있는 수준에서 처리한다.

[Linux/C]
- 시스템 콜과 라이브러리 호출의 반환값은 예외 없이 검사한다. `EINTR`, `EAGAIN`, 부분 읽기/쓰기를 처리한다.
- 에러는 음수 errno 반환 관례를 따른다. 포인터 반환 함수의 에러는 `ERR_PTR` 방식 또는 명시적 출력 인자로 표현한다.
- 정리 경로가 여러 개면 `goto`를 사용한 단일 정리 경로(역순 해제)를 쓴다.

[C/C++]
- 에러 전파 방식은 → D03을 따른다.
- 소유권은 타입으로 표현한다. 단독 소유는 `std::unique_ptr`, 공유 소유는 `std::shared_ptr`(남용 금지), 비소유 참조는 참조·`std::span`·`std::string_view`.
- 핫패스 함수는 `noexcept`를 명시한다.

[Rust]
- 소유권은 시그니처로 말한다: 소유 이전 `T`, 읽기 대여 `&T`, 쓰기 대여 `&mut T`.
- 에러 타입 전략은 → D04를 따른다. `?`로 전파하고, 경계에서 `.context()` 등으로 맥락을 붙인다.
- 라이브러리 코드에서 `unwrap()`/`expect()`는 불변식이 증명된 곳에만 쓰고, `expect`의 메시지에 그 불변식을 적는다.
- 공개 API는 Rust API Guidelines와 semver를 따른다.

---

## 6. 디버깅 (TPOP 5장)

**핵심:** 재현 먼저, 그다음 분할 정복. 추측 대신 관찰.

[공통]
- 버그를 고치기 전에 재현 절차를 확보한다. 재현이 안 되면 재현 조건을 좁히는 것부터 한다.
- 가장 최근의 변경을 먼저 의심한다. 범위를 모르면 `git bisect`로 원인 커밋을 찾는다.
- 익숙한 패턴부터 확인한다: off-by-one, 초기화 누락, 에러 반환 미검사, 수명이 끝난 포인터, 경계 조건.
- 고친 버그는 재현 테스트로 남긴다. 같은 실수를 두 번 하지 않도록 유사 패턴을 저장소에서 검색한다.
- 막히면 문제를 처음부터 글로 설명해 본다(TPOP의 "곰인형에게 설명하기"). 보고서에 가설과 검증 결과를 기록한다.
- 운영 장애 분석에서는 가설 → 관찰 증거 → 결론 순서로 기록하고, 증거 없는 결론을 쓰지 않는다.

[Linux/시스템]
- 관찰 도구 우선순위: 로그 → `strace`(시스템 콜) → `perf`(CPU) → `tcpdump`(네트워크) → 코어 덤프 → `gdb`.
- 성능·장애 분석은 USE Method(사용률, 포화도, 에러)로 모든 자원을 체계적으로 점검한다. 보이는 곳만 보는 "가로등 안티패턴"을 피한다.

[C/C++]
- 메모리·UB·동시성 의심 시 ASan, UBSan, TSan 빌드로 먼저 재현한다.
- 재현이 어려운 버그는 `rr` 기록 재생을 검토한다.

[Rust]
- `unsafe`가 포함된 모듈의 이상 동작은 Miri로 먼저 검사한다.
- `RUST_BACKTRACE=1`, `dbg!`를 쓰되, 커밋 전에 `dbg!`를 제거한다.

## 7. 테스트 (TPOP 6장)

**핵심:** 코드를 쓰면서 테스트한다. 경계 조건, 에러 경로, 스트레스를 검증한다(→ D15).

[공통]
- 경계 조건(0, 1, 최대값, 빈 입력, 가득 찬 버퍼)을 우선 테스트한다.
- 정상 경로보다 에러 경로가 더 위험하다. 연결 끊김, 부분 쓰기, 시간 초과, 디스크 가득 참을 장애 주입으로 검증한다.
- 독립적인 두 구현(단순 참조 구현과 최적화 구현)의 결과를 비교하는 차분 테스트를 활용한다.
- 외부 입력을 파싱하는 코드는 퍼징 대상으로 지정한다.
- 테스트는 자동화되고, 자기 완결적이어야 하며, 회귀 스위트로 유지한다.

[C/C++]
- 테스트 빌드는 새니타이저를 켠 구성을 포함한다.
- 퍼징은 libFuzzer 계열을 기본으로 한다.

[Rust]
- 단위 테스트는 같은 파일의 `#[cfg(test)]` 모듈에, 통합 테스트는 `tests/`에 둔다.
- 공개 API 예제는 doctest로 실행 가능하게 쓴다.
- 속성 기반 테스트(proptest)와 `cargo fuzz`를 파서·직렬화 코드에 적용한다.
- 락프리·원자적 연산 코드는 loom 모델 검사를 적용한다(→ D12).

---

## 8. 성능 (TPOP 7장)

**핵심:** 측정 없이 최적화하지 않는다. 결정적인 3%에 집중한다. 비용 모델의 중심은 연산이 아니라 메모리 접근이다(→ D06).

[공통]
- 최적화 순서: 더 나은 알고리즘·자료구조 → 컴파일러 최적화 옵션 → 코드 튜닝.
- 튜닝 기법(TPOP 목록, 저지연 시스템에서 지금도 유효): 자주 쓰는 값 캐싱, 전용 할당자, 입출력 버퍼링, 특수 케이스 분리, 결과 사전 계산.
- 최적화 전후를 같은 조건에서 측정하고 수치를 보고에 남긴다. 평균만 보지 말고 꼬리 지연(p99, p99.9)을 본다.
- 벤치마크는 운영과 유사한 조건(캐시 상태, 데이터 분포, 동시 부하)에서 수행한다.

[Linux/시스템]
- 시스템 콜 횟수를 줄인다: 배칭, 제로카피(`sendfile`, `splice`), io_uring(→ D08).
- 캐시라인 정렬로 거짓 공유를 막는다. 스레드별 데이터(per-CPU/thread-local)로 공유 자체를 없앤다.
- 분기 예측 힌트는 측정 근거가 있을 때만 쓴다.

[C/C++]
- 제로 오버헤드 원칙: 쓰지 않는 것에 비용을 내지 않는다.
- 핫패스에서는 동적 할당, 예외, 가상 호출, 숨겨진 복사를 피한다. 필요하면 CRTP 같은 정적 다형성을 쓴다.
- 중요한 경로는 생성된 어셈블리를 확인한다(Compiler Explorer 등).

[Rust]
- 이터레이터 체인은 제로 코스트이므로 수동 인덱스 루프보다 먼저 쓴다.
- 핫패스에서 경계 검사가 제거되었는지 어셈블리로 확인한다. `get_unchecked`는 → D11 조건에서만.
- 핫패스에서 힙 할당, `Box<dyn Trait>`, 불필요한 `clone`, `format!`을 피한다.

## 9. 이식성 (TPOP 8장)

**핵심:** 표준에 기대고, 플랫폼 의존 코드는 격리한다(→ D08).

[공통]
- 정수 크기, 부호, 바이트 순서, 정렬, 평가 순서에 의존하지 않는다. 의존해야 하면 명시한다.
- 조건부 컴파일은 최소화하고, 플랫폼 의존 코드는 전용 모듈에 모은다.
- 와이어 프로토콜과 파일 포맷은 바이트 순서와 필드 크기를 명세에 고정한다(→ D09).

[Linux/시스템]
- POSIX 기능과 리눅스 전용 기능을 구분하고, 리눅스 전용 API 사용 지점을 주석으로 표시한다.
- 바이트 순서 변환은 전용 헬퍼(`htobe32` 계열 등)로 한다.

[C/C++]
- 고정 크기 타입(`<stdint.h>`, `<cstdint>`)을 쓴다.
- 부호 있는 정수 오버플로, 엄격한 별칭 규칙 위반, 정렬되지 않은 접근 같은 UB를 피한다.

[Rust]
- 정수 오버플로는 의도를 명시한다: `wrapping_*`, `checked_*`, `saturating_*`.
- 플랫폼 분기는 `#[cfg(...)]`로 구조화한다.

---

## 10. 표기법 (TPOP 9장)

**핵심:** 문제에 맞는 표기법(작은 언어, 스키마, 코드 생성)을 만들면 문제 자체가 쉬워진다(→ D14).

[공통]
- 사람이 손으로 반복해서 쓰는 코드(프로토콜 메시지 정의, 상태 테이블, 직렬화)는 스키마와 생성기로 대체할 수 있는지 검토한다.
- 생성된 코드는 커밋 여부를 정하고(생성기 + 스키마만 커밋 권장), 생성 명령을 빌드에 통합한다.
- 운영 분석용 반복 작업은 스크립트로 만든다. 같은 셸 한 줄을 세 번 쓰면 도구로 만든다.

[Linux/시스템]
- eBPF, awk/sed 파이프라인 같은 작은 언어를 관찰·분석에 활용한다.

[C/C++]
- 컴파일 타임 계산은 `constexpr`/`consteval`로 한다. 템플릿 메타프로그래밍은 가독성 비용을 정당화할 때만.

[Rust]
- derive 매크로(serde 등)를 적극 활용한다. `build.rs` 코드 생성은 입력 스키마가 명확할 때 쓴다.

## 11. 동시성 (TPOP에 없는 10장)

**핵심:** 공유 가변 상태가 동시성 버그의 근원이다. 공유를 없애거나, 공유한다면 규칙을 명시하고 도구로 검증한다(→ D12, D13).

[공통]
- 기본은 소유권 이전(메시지 패싱)이다. 데이터를 공유하지 말고 넘긴다.
- 하나의 데이터는 하나의 스레드만 쓴다(단일 작성자 원칙). 여러 작성자가 필요하면 설계를 먼저 의심한다.
- 락을 쓰면 획득 순서를 문서화하고 지킨다. 락을 잡은 채 I/O나 사용자 콜백을 호출하지 않는다.
- 원자적 연산의 메모리 오더링은 가장 강한 것(`SeqCst`)에서 시작하고, 약화할 때는 근거를 주석으로 남긴다.
- 동시성 코드는 TSan 또는 loom으로 검증하기 전까지 완료로 보지 않는다.

[Linux/시스템]
- 핫패스 스레드는 코어 고정(affinity)과 busy-poll을 검토한다(→ D13).
- 시그널 처리는 signalfd 또는 전용 스레드로 동기 처리한다. 시그널 핸들러에서는 async-signal-safe 함수만 호출한다.

[C/C++]
- C++ 메모리 모델(`std::atomic`, `memory_order`)을 명시적으로 사용한다. `volatile`은 동기화 수단이 아니다.
- 원시 동기화 기법을 직접 쓰기보다 의도가 드러나는 추상화(작업 큐, future 등)로 감싼다(Sean Parent).

[Rust]
- `Send`/`Sync` 경계를 설계 단계에서 정한다. `unsafe impl Send/Sync`는 → D11 조건에서만.
- `Arc<Mutex<T>>`가 코드 전반에 퍼지면 소유 구조 재설계 신호로 본다.
- 비동기 코드에서 블로킹 호출을 하지 않는다. 필요하면 `spawn_blocking` 또는 전용 스레드로 분리한다.

## 12. 위임용 압축본 (서브에이전트 프롬프트에 재기술)

서브에이전트에 코드 작성·분석을 위임할 때, 아래 블록과 **선택 완료된 결정 항목 목록(D## = 선택지)** 을 프롬프트에 함께 붙인다.

```
[Programming Philosophy — Core]
1. 명료함 > 영리함. 함수는 짧게, 한 가지 일만. 새벽 장애 중에 읽힐 코드로 쓴다.
2. 자료구조와 소유 구조를 먼저 정한다. 예외 케이스는 데이터 표현으로 없앤다. 불가능한 상태는 표현 불가능하게.
3. 인터페이스는 작고 직교하게, 올바르게 쓰기 쉽게. 공개 동작은 합의 없이 바꾸지 않는다.
4. 에러는 삼키지 않는다. 복구 가능한 에러는 반환값으로, 불변식 위반은 결정 D05에 따라. 모든 시스템 콜 반환값을 검사한다.
5. 자원 해제는 구조로 강제한다(RAII, Drop, goto 단일 정리 경로).
6. 추측하지 말고 측정한다. 핫패스(D06)는 할당·예외·가상호출·숨은 복사를 피하고 꼬리 지연을 본다.
7. 공유 가변 상태를 피한다. 단일 작성자, 메시지 패싱 우선. 동시성 코드는 TSan/loom 검증 전까지 미완료.
8. UB와 unsafe는 컴파일러와의 계약이다. unsafe는 최소 범위에 가두고 SAFETY 주석을 단다.
9. 버그는 재현 → 분할 정복 → 재현 테스트로 고정. 가설과 증거를 분리해 보고한다.
10. 변경은 논리 단위 하나씩. 커밋 메시지는 "왜"를 쓴다. 스타일 변경과 로직 변경을 섞지 않는다.
```
