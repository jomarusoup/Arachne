# ADR-0003: Dynamic workflows 도입과 3-lane 배치

## 상태

Proposed (채택안 제시 — 사람 승인 대기)

> 2026-08-22 개정: 채택안 **(D)→(A)** 변경. 초판의 (A) 기각 논리("현행 수동 병렬이 결함 발생
> 경로")는 무효 — 그 결함들은 (D)를 채택해도 그대로 남고, 현상의 결함은 결함을 고칠 이유이지 새
> 기능을 도입할 이유가 아니다. 개정판은 "도입 편익" 분석을 신설하고 그 결과로 결론을 바꿨다.

## 결정 질문

Arachne에 Claude Code dynamic workflows(스크립트 기반 다중 에이전트 오케스트레이션, 동시 16
에이전트 규모)를 도입할 것인가. 도입한다면 3-lane 위임 구조(Claude 중심 / Codex tester / Gemini
reader)와 어떤 관계로 배치할 것인가.

## 전제 (감사 `2026-08-22-harness-runtime-audit` 근거)

1. **Q1 미해결 — 컨텍스트 조립 관측 수단 부재(B-10).** rules가 서브에이전트에 주입되는지 실험
   B·보조 수단 모두 (b) 관측 불가로 종료. 본 ADR의 모든 완화책은 **주입 여부 어느 쪽이어도
   성립**해야 한다.
2. **상태 파일 경합 일체** — 무잠금 lost update(C-01), check→act TOCTOU로 쿼터 이중 소모(C-03),
   cross-fs `mv` 비원자(C-02), 비수치 값 무방어(C-04). 저장소 전체에 잠금 0건, 경합 테스트 0건.
3. **git-bus-check의 worktree 상태 분리(C-05·C-06)** — `/worktree` 병렬 실행은 도입 이전에 이미
   동료 커밋 재공지 오탐과 동일 폴더 경합 미탐을 낸다.
4. **B-11 스냅샷 덮어쓰기** — 세션 다중화 자체가 이미 데이터 유실을 낳는다(프로브 실측: 927B
   스냅샷이 426B "브랜치: N/A"로 대체, 복구 불가).
5. [현행 결함] **B-01~B-11**, [도입 제약] **C-01~C-10** 전체 (감사 보고서 "결함 분류" 절).
6. 실측 비용 기준점: 트리비얼 프롬프트 기준 서브에이전트 콜드 스타트 캐시 생성 **25.1k**(planner/
   opus)·**27.9k**(code-reviewer/sonnet) 입력 토큰. 16 에이전트 기본 오버헤드 하한 **≈0.4M 입력
   토큰/실행** [추정 — 실측 콜드 스타트 × 16, 작업 토큰 제외]. 대조: `gtask` 오프로드의 Claude 측
   토큰 소모는 ≈0(래퍼 호출 텍스트뿐).

## 도입 편익 (분석)

(A)를 기각하려면 "현행에 결함이 있다"가 아니라 "(D)가 무엇을 얻어주는가"가 근거여야 한다.

### 1. 읽기 전용 fan-out이 해결하는 현행 문제

특정 가능한 시나리오는 하나다: **대규모 전수 감사·문서-코드-이슈 3자 대조 검증**. 실례 —
본 감사가 발견한 B-03(닫힌 이슈 workflow-06의 수정 방향 미반영)·B-07(훅의 폴백 순서 하드코딩
중복)·MULTI-CLI 쿼터 키워드 표 드리프트는 전부 병렬 다각 탐색이 찾은 대조 결함이고,
`e9d31bd`(SYNCTHING-SETUP 전수 검증)류 작업이 반복 수요다.

그러나 **편익의 귀속**이 문제다: 본 감사는 dynamic workflows 없이 **기존 Agent 도구
fan-out(병렬 에이전트 5개)으로 수행됐다.** 발견 실적(B-01~11·C-01~10)은 이미 보유한 능력의
실적이지 도입될 능력의 실적이 아니다. dynamic workflows의 증분은 결정론 제어(loop-until-dry·
다수결 검증·중복 제거 장벽)와 5개 초과 규모인데, 저장소 이력의 감사류 산출물 6건
(`docs/issue/*audit*`·`*evaluation*` 5건 + 본 감사)은 전부 그 증분 없이 완료됐다 — 증분이
필요했던 실사례 0건.

### 2. 현행 처리 방식과의 비교

- 현행: ① 대량 읽기 → `gtask` 오프로드(Claude 토큰 ≈0, 정밀도 낮음), ② 정밀 판정 → 메인 세션 +
  Agent 도구 병렬(회당 3~5 에이전트), ③ `/worktree` 수동 병렬은 **수정형 작업 분담용이며 읽기
  감사에는 쓰이지 않는다** — 초판 (A) 기각 논리는 비교축 자체가 성립하지 않았다.
- (D)가 나아지게 하는 것: 오케스트레이션 자동화(단계 재촉·중간 취합의 사람 개입 감소), 판정
  다수결. 나아지지 않는 것: 발견 능력의 하한(Agent 도구로 이미 확보), 오프로드 비용 구조,
  B-01~11(어느 선택지에서도 그대로 남음).

### 3. 대상 커맨드 특정과 비용 정당화

"읽기 전용·검증 커맨드"를 실제 커맨드명으로 열거하면:

| 커맨드 | 예상 실행 빈도 (근거) | 적용 시 증가/실행 | 기간당 총 증가 |
| --- | --- | --- | --- |
| `/verify` | 주 2~5회 [커밋 전 필수 규약(`git-workflow.md`) → 커밋 빈도와 동일; 최근 커밋 이력 기준 추정] | +0.4M 하한 (현행: 린터·테스트 직접 실행으로 에이전트 0) | **주 0.8~2.0M** |
| `/python-review` `/fastapi-review` `/react-review` `/database-review` | Arachne 자체 0회(대상 언어 파일 없음); 사용 프로젝트 빈도는 **측정 불가**(호출 기록 부재) | 현행 단일 리뷰어 ~30k → +0.3M+ (10배+) | 측정 불가 |
| `/codegraph` | — | 적용 무의미 — 외부 도구 래퍼, fan-out 아님 | 0 |
| `/e2e` | 주 0~1회 | 적용 부적합 — 병목이 테스트 실행이지 에이전트 아님 | 0 |
| 감사·전수 검증 | 월 ~2회 [`docs/issue/` 감사류 6건 / 2026-06~08 3개월] | +0.4M~ | 월 ~0.8M |

핵심 관찰 둘:

1. **(D)의 유일한 실질 수혜 작업(감사·전수 검증)에는 커맨드가 없다** — ad-hoc 프롬프트로
   수행된다. "특정 커맨드에서만 활성화"의 적용 대상이 사실상 공집합이며, (D)는 커맨드 신설을
   전제해야만 정의된다.
2. **오프로드 절약량과의 비교: 측정 불가.** `gtask`/`ctask` 래퍼는 호출 이력·토큰량을 어디에도
   기록하지 않는다. 재야 할 것: 래퍼 호출 시각·프롬프트/응답 크기의 append-only 로그 4주.
   상한 추정만 가능: 오프로드 1회가 절약하는 Claude 토큰 ≈ 콜드 스타트+읽기 분량(실측 하한
   25k) → 주 10회 호출 가정 시 절약 ≈ **주 0.25M+α**.

**`/verify` 단독 판정**: 주 3회만 잡아도 3 × 0.4M = **주 1.2M 증가**로, 위 절약 상한 추정(주
0.25M+α)을 **단독으로 초과·상쇄**한다. → `/verify`는 어떤 채택안에서도 워크플로 대상에서
제외한다.

**정당화 판정**: 0.4M/실행 자체는 월 ~2회 감사 기준 감당 가능한 절대량이나, 그 지출이 사는
것이 "이미 보유한 능력의 자동화 편의"뿐이고 증분 능력(결정론 루프·5+ 규모)의 필요 실사례가
0건이며 비용 비교는 계측 부재로 측정 불가다. **편익이 도입을 정당화하지 못한다 → 결론을 (A)로
변경한다.**

## 선택지 비교

각 선택지에 대해 감사 지정 6개 질문에 답한다.

### (A) 도입하지 않는다 — 현행 3-lane 유지

1. **깨지는 것**: 신규로는 없음(동시 16을 얹지 않음). 단 "현상 유지 = 무결함"이 아님 — C-05·C-06은
   `/worktree` 다중 세션에서, B-11은 세션 2개(프로젝트 무관)에서 이미 발현 중. B-01~11은 도입과
   무관하게 수리 대상으로 잔존.
2. 오프로드 사슬 유지. 비용 변화 **0**.
3. 유지 — 단일 세션 단일 diff, 압축 메커니즘 불요.
4. C-08 이관은 (A)에서도 여전히 권장(가치가 도입과 무관)이나 규모 압력이 없어 우선순위만 낮아짐.
5. 충돌 없음.
6. 해당 없음 — 단 B-10은 "현행 규율이 적용되는지 스스로 검증 불가"라는 공백으로 남는다.
- **기회비용**: "도입 편익" 분석 참고 — 읽기 감사에 `/worktree` 수동 병렬은 실제로 쓰이지 않으며
  (수정형 분담용), 현행 처리(gtask 오프로드 + Agent 도구 fan-out)가 감사 수요를 이미 충족하고
  있어 (A)의 기회비용은 "오케스트레이션 자동화 편의"에 한정된다.

### (B) 선결조건 해소 후 도입

1. **깨지는 것(선결조건 미충족 상태에서 얹을 경우)**: C-01 쿨다운 기록 소실 → 소진 CLI 재타격,
   C-03 최대 16× 쿼터 이중 소모(사후 기록 구조라 원천 방지 불가), C-02/C-04 부분 기록 → 가용 오판,
   비격리 에이전트 2개의 동일 파일 Edit 충돌, 다중 세션 병용 시 B-11 유실. **충족 후**: 각 항목이
   아래 PC 체크리스트의 테스트로 봉인되므로 깨지지 않는다 — 근거는 서술이 아니라 통과하는 테스트.
2. **조건부 무력화**: read-heavy 단계를 워크플로에 넣으면 사슬 우회(에이전트당 25k+ 하한 vs Gemini
   0). 정책으로 read-heavy를 `gtask`에 남기면 비용 증가는 검증·리뷰 단계에 국한 — **+0.4M 하한/실행**.
3. **유지 가능 — 조건 3개**: ① 수정형 워크플로는 worktree 격리 의무, ② 종단 synthesis 단계가
   "파일별 변경 요약 + worktree별 `/verify` 결과"를 단일 문서로 산출, ③ 커밋은 메인 세션이 worktree
   단위 순차 수행. 사람 검증 대상은 N개 원시 diff가 아니라 (a) synthesis 요약 (b) verify 판정표
   (c) 고위험 diff 스팟체크 1~2건 — 이 압축 계약을 해당 커맨드 문서에 명문화한다.
4. 아래 PC-7 (구조 계층 배치는 (D)의 4번과 동일 원칙).
5. 충돌 없음 — 조건: 워크플로 서술은 CLAUDE.md·커맨드 계층에만 두고 `AGENTS.md` 본문 불변.
6. 허용 — 근거: 게이트를 관측 불가한 컨텍스트가 아니라 **관측 가능한 산출물**(CI·verify 리포트·
   실행 기록)에 둔다. B-10은 디버깅 제약으로 남지만 도입 차단 사유는 아니다.

**선결조건 체크리스트** (각 항목의 완료 판정은 검증 가능 형태):

### (C) 배타적 도입 — 워크플로 실행 중 gtask/ctask 위임 금지

1. C-01~04는 "호출 금지"로 회피되는 듯 보이나 금지 자체가 강제 불가(4번) → 회피 보장 없음. 확실히
   깨지는 것: **Claude 쿼터 집중** — 16 에이전트 × (25k 콜드 스타트 + 작업 토큰)이 전부 단일 5h
   창에서 소모되고, 소진 시 `COOLDOWN_CLAUDE=18000s`(5h) 동안 중심 레인이 정지한다. 가용성 폴백

### (D) 계층 분리 — 특정 커맨드에서만 워크플로 활성화

범위 정의: **읽기 전용·검증 성격 커맨드**(감사, 전수 검증, 다차원 리뷰, 대규모 조사)에만 워크플로
허용. 수정형 작업은 현행 3-lane 유지.

1. **깨지는 것 없음 — 조건부**: 읽기 전용이면 파일 충돌·git 경합이 원천 부재(쓰기 없음). 상태
   경합은 에이전트가 atask/래퍼를 부르지 않는 한 없음 — 이 경계도 프롬프트 계층이지만 blast
   radius가 "부정확한 보고서"로 한정되고 산출물이 사람 검토를 거친다. 잔존 리스크(에이전트 Bash의
   상태 파일 접근)는 PC-7의 PreToolUse 훅이 커버하되, 보장 수준은 PC-8 결과로 확정된다.
2. **보존** — read-heavy 대량 요약은 종전대로 `gtask`(사슬 유지), 워크플로는 Claude 정밀도가 필요한
   판정·검증·교차검증 단계 전용. 비용 증가는 허용 커맨드 실행 시에만 **+0.4M 하한/실행** [실측
   콜드 스타트 기반 추정].
3. **유지** — 읽기 전용 워크플로는 diff를 생성하지 않으므로 압축 문제 자체가 없다. 커밋은 종전대로
   메인 세션의 단일 diff. (수정형은 이 선택지 범위 밖 — (B) 게이트로 미룸.)
4. **구조 계층 배치**: ① 워크플로 허용 커맨드에만 해당 도구를 여는 `allowed-tools`
   frontmatter(현재 19개 커맨드 전부 부재 — 신설), ② 전역 PreToolUse 훅으로 파괴적 Bash 패턴 차단
   (호출 주체 무관), ③ 커밋 게이트는 기존 CI(`.arachne/verify.sh`·Actions). **스크립트 내부 선언에는
   어떤 강제 역할도 부여하지 않는다.**
5. **충돌 없음** — 슬래시 커맨드는 `AGENTS.md:12-14`가 이미 "Claude 전용 보충 계층"으로 선언한
   위치다. `AGENTS.md` 본문 무변경, 최종 게이트는 CI로 전 CLI 동일(`AGENTS.md:173-179` 유지).
6. **허용** — 근거: 관측 불가 계층(컨텍스트) 위에 얹는 것은 병렬 *수정*이 아니라 병렬 *보고서
   생성*이며, 게이트는 관측 가능한 계층(산출물의 사람 검토 + 인용 스팟체크)에 있다. 이 근거는
   수정형에는 성립하지 않으므로, 수정형 확장은 (B) 체크리스트 충족 전 금지.

## 재평가 트리거 · 반증 조건 (이 결정이 틀렸음을 알게 되는 관측)

1. Agent 도구 fan-out으로 수행한 감사·전수 검증이 **놓친 결함이 사후 발견되는 사례가 2회
   문서화**되고(`docs/issue/`), 원인 분석이 "규모·반복 탐색 부족"(loop-until-dry·다수결 검증이
   있었으면 잡혔을 것)으로 귀결되면 — "증분 편익 부재" 판단이 틀림. → (B) 경로 재평가,
   PC-1~PC-10 발효.
2. 계측 4주 축적 후: 감사류 작업 빈도가 **월 4회 이상**으로 증가하고, 오프로드 절약 실측이
   워크플로 예상 비용 하한(+0.4M/실행)과 같은 자릿수로 확인되면 — 비용 반대 근거 약화. → 재평가.
3. **기준선 부재 명시**: 초판 반증 조건에 있던 "쿨다운 진입 빈도 도입 전 대비 2배" 류의 빈도
   조건은 **도입 전 기준선이 측정된 적이 없어 현재 작동하지 않는다.** `arachne-quota-state`는
   최신 쿨다운만 보존하고 진입 이력을 남기지 않으며, 래퍼는 호출 기록이 없다. 기준선 확보 방법:
   위 계측 2건(append-only 이력 — 구현 방식 자유)을 도입 논의와 무관하게 지금 시작해 4주 축적한다.
   **축적 완료 전에는 빈도·배수 기반 조건 일체가 판정 불능**이며, 이는 향후 (B)/(D) 재평가에서도
   선행 조건이다.
