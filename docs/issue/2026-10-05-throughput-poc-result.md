# [poc] TS(Node) 스트림 수신 처리량 실측 — D-02 확인

- **작성일**: 2026-10-05
- **영역**: 로드맵 §5.D-6 PoC, §3 D-02(데스크톱 클라이언트 언어)
- **상태**: done (같은 호스트 측정 완료, 실제 네트워크·Windows 측정은 후속)
- **템플릿**: `templates/project/throughput-poc/`, 방법론 `skills/load-testing/SKILL.md`

## 결론

**Node 수신기는 1만·10만·100만 건/초를 모두 버텼다.**
64바이트 메시지 기준으로 유실 0, 달성률 100%, p99 0.25ms 이하였다.

**포화점은 1,000만~2,000만 건/초 사이다.**
2,000만 건/초를 목표로 주면 약 1,660만 건/초(약 1.1GB/s)에서 멈췄다.
요구 상단인 100만 건/초 대비 10배 이상 여유가 있다.

**D-02는 TS(Electron)로 확정하는 것을 권고한다.**
C# 트랙(E-5)은 열지 않는다.
다만 실제 네트워크·Windows·디코딩 포함 측정에서 재검토 조건이 걸리면 다시 연다(아래 권고 참고).

## 환경

| 항목 | 값 |
|---|---|
| 기계 | Apple M1 Max, 10코어, 메모리 32GB |
| OS | macOS 26.5.1 |
| 전원 | AC 전원 연결 (`pmset -g batt`: AC Power) |
| 컴파일러 | Apple clang 21.0.0, `-O2` |
| Node | v26.10.0 |
| 연결 | 같은 호스트 `127.0.0.1` TCP, 송신·수신 각 1프로세스 |
| 메시지 | payload 64B (와이어 프레임 68B) |

## 방법

- **송신기**: C 송신 시뮬레이터(`sender/poc_sender.c`)가 개방 루프로 보낸다.
  메시지 n의 예정 시각은 `start + n / rate`다.
  일정보다 밀리면 최대 1024 프레임을 한 `write`로 묶는다. `TCP_NODELAY`를 켰다.
- **와이어 형식**: `[u32 BE 길이][payload]`. payload에 시퀀스와 예정 송신 시각이 들어 있다.
  `c-system/src/pipeline/frame_codec`과 같은 프레이밍이다.
- **Node 수신기**: `net` 소켓 chunk를 재사용 버퍼에 이어 붙이고 완성 프레임만 해석한다.
  메시지별 할당을 피하려고 u64는 `readUInt32LE` 두 번으로 읽는다.
  지연은 `process.hrtime.bigint()` 수신 시각에서 예정 송신 시각을 뺀 값이다.
- **같은 시계 확인**: 송신기는 macOS에서 `CLOCK_MONOTONIC_RAW`를 쓴다.
  Node `hrtime`과 같은 시계임을 실측으로 확인했다(HELLO 수신 시 차이 0.5~0.6ms).
  처음 쓴 `CLOCK_UPTIME_RAW`는 잠자기 시간만큼 약 2만 8천 초 어긋났다.
- **C 기준선**: 같은 형식을 같은 방식으로 받는 C 수신기(`receiver-c/poc_receiver.c`)를 함께 돌렸다.
- **지속 시간**: 기본 3단계는 레이트당 10초, 포화점 탐색은 5초.
- **정확성 점검**: ASan+UBSan 빌드로 20만 건/초 2초를 먼저 돌려 오류가 없음을 확인했다.

## 해석 (D-02)

**TS 수신기는 요구 범위를 여유 있게 버틴다.**
1만~100만 건/초에서 Node와 C의 p50·p99는 같은 자릿수다.
꼬리(p99.9 수 ms)도 C 기준선과 비슷하다. 같은 호스트에서 송신기와 코어를 다투는 영향이 크다는 뜻이다.

**포화는 단일 스레드 CPU에서 온다.**
2,000만 건/초에서 CPU가 100%에 붙고, 수신 시간이 예정보다 1초 늘었다.
이때 p50이 430ms로 뛰었다. 전형적인 포화 신호다.
포화 처리량으로 보면 메시지당 해석 비용은 약 60ns다(1코어 ÷ 1,660만).

**CPU%는 메시지 수보다 chunk 수를 따른다.**
Node CPU는 100만 건/초에서 이미 85%이지만, 1,000만 건/초에서도 94%였다.
레이트가 오르면 chunk 하나에 담기는 메시지가 늘어 이벤트당 비용이 분산되기 때문이다.
따라서 "CPU 85%"를 "여유 15%"로 읽으면 안 된다. 실제 여유는 포화점 기준 10배 이상이다.
반대로 레이트가 낮아도 송신 측이 메시지마다 `write`하면 수신 CPU가 높아진다.
서버는 프레임 단위로 묶어 보내는 편이 클라이언트 CPU에 유리하다.

**GC는 꼬리 지연의 주원인이 아니었다.**
최대 GC 정지가 0.8ms 이하였다. 수신 경로에서 메시지별 할당을 없앤 효과다.
GC 횟수 대부분은 Node가 chunk마다 만드는 `Buffer`에서 나온다.

**Electron utility process에 주는 뜻은 다음과 같다.**
utility process는 같은 Node·V8 런타임이므로 수신·해석 단계는 이 수치를 그대로 기대할 수 있다.
병목은 수신이 아니라 그 뒤 단계가 될 것이다.
100만 건/초를 렌더러로 메시지 단위 `postMessage`하면 버티지 못한다.
utility process가 최신 상태로 모으고, 화면 주기(예: 60Hz)에 스냅샷·차분을 묶어 넘겨야 한다.
`SharedArrayBuffer` 링버퍼나 transferable `ArrayBuffer`로 복사를 줄인다(로드맵 C-2 범위).

## 측정의 한계

- **같은 호스트(localhost)다.** 네트워크 지연·대역폭 한계·재전송·NIC 인터럽트가 빠져 있다.
  1GB/s를 넘는 포화점은 루프백에서만 가능한 값이다.
  실제 1GbE(약 125MB/s)라면 68B 프레임 기준 약 170만 건/초가 회선 한계다.
  즉 실제 회선에서는 Node 수신기보다 네트워크가 먼저 막힌다.
- **송신기와 수신기가 같은 기계의 코어를 나눠 쓴다.** p99.9의 수 ms 꼬리는 C 기준선에도 있으므로 상당 부분 이 영향이다.
- **macOS M1 Max 한 대다.** 실제 데스크톱 대상인 Windows와 저사양 노트북은 재지 않았다.
  Windows는 소켓 스택과 타이머 해상도가 달라 꼬리 지연이 다를 수 있다.
- **해석만 했다.** 실제 클라이언트의 디코딩(필드 해석·정수 스케일 변환), 상태 갱신, 렌더러 전달 비용은 빠져 있다.
- **짧은 측정이다.** 레이트당 10초(포화 탐색 5초), 1회씩이다. 1시간 안정성(RSS 추세)은 재지 않았다.
  100만 건/초 10초 동안 RSS가 21.4MB에서 25.0MB로 올랐으므로 장시간 추세는 따로 확인해야 한다.
- **Electron 자체로 재지 않았다.** 일반 Node v26으로 쟀다. Electron 내장 Node는 버전이 다를 수 있다.

## 권고

1. **D-02를 TS(Electron)로 확정한다.** 수신 성능은 C# 트랙을 열 근거가 되지 않는다.
2. **C# 트랙(E-5)은 대기 상태로 둔다.** 다음 중 하나라도 걸리면 다시 연다.
   - 실제 네트워크 두 호스트 측정에서 요구 레이트 × 2를 못 버틴다.
   - Windows 대상 하드웨어에서 요구 레이트의 p99가 10ms를 넘는다.
   - 디코딩·상태 갱신을 넣은 utility process가 요구 레이트에서 CPU 100%에 붙는다.
3. **후속 측정(W4, C-2와 함께)**
   - Electron utility process 안에서 같은 수신기를 돌린다(`NODE_BIN`에 Electron 경로, `ELECTRON_RUN_AS_NODE=1`).
   - Windows 대상 기기와 실제 네트워크 두 호스트로 다시 잰다.
   - 디코딩 + 렌더러 묶음 전달 단계를 넣고 1시간(`DURATION=3600`) 안정성을 잰다.
4. **서버 송신 규약**: 서버는 프레임 단위로 묶어 보낸다. 메시지마다 `write`하지 않는다.
   이것이 클라이언트 CPU를 가장 크게 줄인다.
